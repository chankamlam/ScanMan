## 0. 结论速览

**一句话**：**预处理流水线的工程实现是合格的（防泄漏设计 A 级、跨平台可复现），但原始数据本身存在三类严重质量问题，且预处理环节存在一个"设计失效"和一个"指标失真"问题。**

### 六个最重要的数字

| # | 发现 | 实测值 | 影响 |
|--:|------|-------:|------|
| **1** | **原始数据里约 26% 的记录代码字段是空的** | `vulnerable_code` 空 22.41%，`fixed_code` 空 7.88%，两者都空 7.17% | 12,987 条原始记录只能展开出 22,039 条样本，最终剩 18,925 条 |
| **2** | **代码长度有极端离群值** | `vulnerable_code` 最长 **55,330,596 字符**（55 MB），第 99 百分位 = 214,996 | 均值被拉到 30,753，中位数只有 233 —— **均值毫无意义** |
| **3** | **测试集 87.80% 是"同胞对"样本** | 1,902 条里 1,670 条来自"同一提交含漏洞版+修复版"的分组 | 评测虚高的根源：模型擅长"比较两行差异"，不是"发现新漏洞" |
| **4** | **约 27% 的样本超过模型 512 词元窗口** | 训练集 **26.57%** / 验证集 27.24% / 测试集 28.55%（**真实分词器实测**） | 构建阶段的"头尾截断"设计在这些样本上**实际失效** |
| **5** | **字符/词元比实测 2.28，而非粗估的 3.8** | 偏差 −40% | 用粗估比值会低估超窗比例 7 个百分点（19.4% vs 26.6%） |
| **6** | **分类任务 OTHER 类占 18.76%，与最大真实类相当** | OTHER 1,094 条 vs CWE-79 1,103 条；测试集最小类只有 **1 条** | 宏平均 F1 会被长尾类主导，指标剧烈抖动 |

### 评分卡

| 维度 | 评分 | 依据 |
|------|:----:|------|
| 防泄漏设计（分组划分） | **A** | `group_id` 交叉 train∩val∩test = **0 / 0 / 0**，MD5 交叉 = **0** |
| 可复现性 | **A** | 复现脚本重跑：22,039 → 21,041 → **18,925**，与 `stats.json` 逐条一致 |
| 原始数据完整性 | **C** | `severity` 有 4,799 条是字符串 `"nan"`（36.95%），不是真空值；代码字段空值率高 |
| 异常值治理 | **C-** | 55 MB 的代码字段未在源头拦截，靠构建阶段截断兜底 |
| 预处理实现正确性 | **C** | 截断逻辑被分词器覆盖（设计失效）；两处 `max_code_chars` 配置易漏改 |
| 评测有效性 | **D** | 测试集 87.8% 为同胞对，指标无法预测真实能力 |

### 1.2 为什么坚持"不改原代码"

这是**有意的设计选择**，原因有三：

**① 分析不应当污染被分析的对象。**
如果把审计统计直接塞进 `build_dataset.py`，那么"数据集"和"对数据集的描述"就耦合了 ——
下次重建数据时审计逻辑会跟着一起改，历史数字就对不上了。

**② 保持可复现性。**
`build_dataset.py` 的现有实现能稳定产出 18,925 / 15,147 / 1,876 / 1,902，
这个数字和 `cvefixes_stats.json`、和文档、和云端训练记录**完全一致**。
改动它会让所有历史结论失去参照。

**③ 便于交付与评审。**
新增的 `analysis/` 是一个自包含的只读工具目录，
可以整体拷走、单独运行、单独评审，不影响项目主流程。


### 2.3 关键设计：group_id 防泄漏

这是整个预处理**最正确的一个决策**。

```
group_id = "cvefixes::<cve_id>::<commit_hash>"
```

同一 CVE 的同一提交产出的「漏洞版」与「修复版」共用同一个 `group_id`，
划分时**以分组为单位**而不是以样本为单位，保证这两个版本**永远落在同一个集合**。

**为什么必须这样**：`vulnerable_code` 与 `fixed_code` 往往只差几行，
如果按样本随机划分，测试集里就会出现训练集的"近邻副本"，F1 能虚高到 0.99。

**实测验证（三个层级都查了）**：

| 检查项 | 交叉数 | 判定 |
|--------|-------:|------|
| `group_id` 交叉 训练集∩验证集 | **0** | ✅ 通过 |
| `group_id` 交叉 训练集∩测试集 | **0** | ✅ 通过 |
| `group_id` 交叉 验证集∩测试集 | **0** | ✅ 通过 |
| MD5 指纹交叉 训练集∩测试集 | **0** | ✅ 通过 |
| 去空白指纹交叉 训练集∩测试集 | 3（占测试集 0.16%） | ⚠️ 轻微（只差缩进/空行的近重复） |

> **复现命令**：`python analysis/audit_data.py` → 第二段

### 3.1 缺失（Missing）

#### 3.1.1 原始数据逐字段缺失率（实测）

| 字段 | 真正的空值 | 空字符串 | **字符串 `"nan"`** | 合计缺失率 |
|------|-----------:|--------:|------------------:|----------:|
| `cve_id` | 0 | 0 | 0 | 0.00% |
| `hash` | 0 | 0 | 0 | 0.00% |
| `repo_url` | 0 | 0 | 0 | 0.00% |
| `cwe_id` | 0 | 0 | 0 | 0.00% |
| `cwe_name` | 0 | 0 | 0 | 0.00% |
| `language` | 0 | 0 | 0 | 0.00% |
| **`vulnerable_code`** | 0 | **2,911** | 0 | **22.41%** |
| **`fixed_code`** | 0 | **1,024** | 0 | **7.88%** |
| `commit_message` | 0 | 8 | 0 | 0.06% |
| `cve_description` | 0 | 0 | 0 | 0.00% |
| **`severity`** | 0 | 0 | **4,799** | **36.95%** |
| **`cvss3_base_score`** | **1,978** | 0 | 0 | **15.23%** |
| `commit_date` | 0 | 0 | 0 | 0.00% |
| `file_paths` | 0 | 937 | 0 | 7.21% |

**三个必须注意的点**：

**(1) 代码字段的缺失是"空字符串"而不是真正的空值。**
`vulnerable_code` 有 2,911 条空串、`fixed_code` 有 1,024 条空串。
如果只检查 `isna()` 会得出"零缺失"的错误结论 —— **必须同时检查空字符串**。

**(2) ⚠️ `severity` 字段的 `"nan"` 陷阱（最容易踩的坑）。**
4,799 条（**36.95%**）的 `severity` 值是**字符串 `"nan"`**，而不是真正的空值。
**如果按 `severity` 做分组统计，会把 `"nan"` 当成一个真实类别**，得到错误结论。

**(3) `cvss3_base_score` 是真的空值（1,978 条）。**
这是唯一一个用真空值表示缺失的字段 —— 说明**同一份数据里存在三套缺失表示法**，
这在数据接入时是典型的"需要逐字段确认"场景（见图 18）。

#### 3.1.2 处理后数据的缺失

预处理后的 JSONL **不缺失**（10 个字段全部非空），因为：
- `id` / `code` / `label` / `source` / `group_id` / `code_hash` 由构建脚本生成，必然有值
- `cwe` / `cwe_name` 对安全样本（label=0）**故意留空**（安全代码没有漏洞类型）
- 空代码的记录在展开阶段就被丢弃了

### 3.2 异常（Anomaly）

#### 3.2.1 ★ 代码长度异常：极端离群值

| 指标 | `vulnerable_code` | `fixed_code` |
|------|------------------:|-------------:|
| 中位数 | **233** 字符 | **666** 字符 |
| 均值 | **30,753** 字符 | **36,733** 字符 |
| 第 90 百分位 | 3,046 | 6,959 |
| 第 99 百分位 | **214,996** | **284,538** |
| **最大值** | **55,330,596** | **55,327,652** |

> ### ⚠️ 均值和最大值之间差了 5 个数量级
>
> **中位数 233 vs 均值 30,753 —— 均值是中位数的 132 倍。**
> 这说明分布极度右偏，**任何基于均值的统计（平均长度、总长度）都毫无意义**，
> 必须用中位数和分位数。这也是为什么图 1、图 6 全部用 **对数轴**。
>
> **最大值 55,330,596 字符 ≈ 55 MB**，单个字段的值比整个 parquet 文件的四分之一还大。
> 这不是"长函数"，而是**上游解析失败把整个文件内容塞进了一个字段**。
> 这类脏数据**应该在接入时拦截**，现在靠构建阶段的 20,000 字符截断兜底。

**超长样本的实际影响面**（阈值 = 512 词元 × 实测 2.28 字符/词元 ≈ **1,168 字符**）：

| 阈值 | `vulnerable_code` 超出 | `fixed_code` 超出 |
|------|----------------------:|------------------:|
| > 20,000 字符（构建阶段截断阈值） | 282（**2.82%**） | 420（**4.21%**） |
| > 1,168 字符（≈512 词元） | 1,388（**13.90%**） | 2,751（**27.56%**） |

#### 3.2.3 字段取值异常

|--------|------|

### 3.3 重复（Duplicate）

#### 3.3.1 原始数据的重复

| 检查项 | 数量 | 说明 |
|--------|-----:|------|
| 记录总数 | 12,987 | — |
| 唯一 `cve_id` | **11,726** | 重复 1,261 条 |
| 唯一提交 `hash` | **11,859** | 重复 1,128 条 |

**这不是数据错误，而是数据的固有结构**：一个 CVE 可能有**多个修复提交**
（比如先修一处，后来发现漏了再补一次），所以同一个 `cve_id` 会出现多次。

> ⚠️ **这正是 `group_id` 要用 `cve_id + hash` 两个字段的原因**。
> 如果只用 `cve_id` 分组，同一个 CVE 的**不同提交**会被强制分到一起，划分会失衡；
> 如果只用 `hash`，又会把不该拆的拆开。

#### 3.3.2 预处理后的重复（三层去重效果）

| 层级 | 手段 | 剔除量 | 结果 |
|------|------|-------:|------|
| ① 展开 | 代码字段为空的记录不产出样本 | 931 条记录 | 22,039 条样本 |
| ② 长度过滤 | `len(code) < 30` 丢弃 | **998 条**（4.53%） | 21,041 条 |
| ③ MD5 去重 | `md5(code)` 相同只留一份 | **2,116 条**（10.06%） | **18,925 条** |

**去重能力评测（本次实测，见图 19）**：

| 去重手段 | 抓到的重复 | 漏掉的 |
|----------|-----------:|--------|
| MD5（逐字节相同） | 2,116 条 | — |
| 去空白指纹 训练集∩测试集 | — | **3 条**（占测试集 0.16%） |
| 去空白后同集合内重复 | 训练集 **13 条**、测试集 **1 条** | — |
| **标签冲突**（同一段代码同时带 0 和 1） | — | **8 处** |

**结论**：
- ✅ **MD5 去重是有效的**（剔除了 10%），且训练集∩测试集的 MD5 交叉为 **0**
- ⚠️ **MD5 只能抓"逐字节完全相同"**，抓不到"只差缩进/空行/注释"的近重复（3 条，可忽略）
- ⚠️ **仍有 8 处标签冲突**：同一段代码同时出现在 label=0 和 label=1，
  模型在完全相同的输入上会收到相反的梯度。数量很少，影响有限

> **对比说明**：同一套方法用在 BigVul 上时，近重复泄漏是 **538 条（3.35%）**，
> CVEfixes 只有 **3 条（0.16%）**。**收敛到单数据源后，近重复问题的紧迫性大幅下降。**

  但**长尾部分有超过四分之一的样本超窗**

> ### ⚠️ 这是本报告发现的第二个严重问题：截断设计失效
>
> 项目的 `src/utils.py::truncate_code()` 实现了「头 60% + 尾 40%」截断，设计意图是
> **保留函数尾部的 `free()`、边界检查、`return`**（漏洞关键信息集中在首尾）。
>
> **但实际的截断链条是这样的**：
> ```
> ① build_dataset.py: truncate_code(code, 20000)   ← 字符级，头60%+尾40%
> ② src/data.py:       truncate_code(code, 8000)    ← 又截一次，同样规则
> ③ tokenizer(truncation=True, max_length=512)      ← ★ 从尾部砍！
>    ❌ 第 ② 步精心保留的"尾部"被整段砍掉了
> ```
> **`model.max_code_chars = 8000` ≈ 3,500 词元，远超 512 的窗口。**
> 所以第 ③ 步会把第 ② 步保留的尾部再砍一次，**头尾截断的设计在超窗样本上完全失效**。
>
> **影响面：约 27% 的训练样本**（实测，非估算）。
>
> **修复方案（改动 1 行）**：把 `model.max_code_chars` 从 8000 降到 **1600**
> （1168 字符 + 余量），或改在 **词元级别**做头尾拼接。

## 5. 关键发现：五个必须知道的问题

### 5.1 【严重】截断设计失效（图 11）

| 项 | 内容 |
|----|------|
| **现象** | 「头 60% + 尾 40%」的截断设计在超窗样本上完全失效 |
| **原因** | `model.max_code_chars = 8000`（≈3,500 词元）远超 512 的窗口，分词器的 `truncation=True` 从尾部砍，把保留的尾部又砍掉了 |
| **影响面** | **26.57% 的训练样本**（实测 797/3000） |
| **修复** | `configs/config.yaml` 里 `model.max_code_chars: 8000` → **1600**（改动 1 行） |
| **代价** | 需要重建数据 + 重训（4090D 上约 15 分钟） |
| **为什么重要** | 这是唯一一个"文档已经把病灶和药方都写清楚、却一直没执行"的改动 |

### 5.2 【严重】测试集被同胞对主导（图 12）

| 项 | 内容 |
|----|------|
| **现象** | 1,902 条测试样本里 **1,670 条（87.80%）** 是"同一提交的漏洞版+修复版" |
| **后果** | F1=0.75 衡量的是"比较两行差异"，不是"发现新漏洞"。孤立样本（232 条）漏洞占比仅 **7.76%** |
| **修复** | 建"干净测试集"：剔除成对分组，只用 232 条孤立样本评估 |
| **预期** | F1 会从 0.745 掉到 **0.35~0.55** —— 掉下来的就是幻觉 |
| **注意** | 232 条太少（置信区间 ±0.06），需要从其他数据集补到 ≥1,000 条 |

### 5.3 【严重】分类任务长尾与 OTHER 膨胀（图 13、15）

| 项 | 内容 |
|----|------|
| **现象** | OTHER 占 18.76%（1,094 条，与最大真实类相当）；23 个类的测试样本 < 10 条；最小类只有 1 条 |
| **后果** | 宏平均 F1 剧烈抖动；OTHER 是上百种不相干类型的垃圾桶，无行动价值 |
| **修复** | ① 主指标改加权 F1 或只对样本数 ≥ 20 的类算宏平均<br>② `min_class_samples` 从 30 提高到 60~100<br>③ OTHER 改层级类型或加拒答机制 |
| **实测对比** | 全部 41 类宏平均 = **0.1979**；只算样本数 ≥ 5 的 34 类 = **0.2237** |

### 5.4 【中】原始数据的脏值未在源头拦截（图 1、18）

| 项 | 内容 |
|----|------|
| **现象** | 代码字段最大 **55 MB**；`severity` 用字符串 `"nan"` 表示缺失（36.95%）；`language` = `Unknown` 占 7.21% |
| **后果** | 均值统计失真（均值是中位数的 132 倍）；按严重级分组会得到错误结论 |
| **修复** | 在 `build_cvefixes()` 里加长度上限断言（如 >200KB 直接丢弃并记日志）；文档里显式标注 `severity` 的 nan 陷阱 |

### 5.5 【中】用经验值估算词元数会带来 40% 偏差（图 10）

| 项 | 内容 |
|----|------|
| **现象** | 粗估"3.8 字符/词元"，实测是 **2.28** |
| **后果** | 超窗样本比例被低估 7 个百分点（19.4% vs 26.6%） |
| **教训** | **凡是能实测的，不要用经验值。** 本项目已经加载了分词器，测一次只要 2 秒 |
| **已修正** | 绘图脚本改为运行期实测比值并回填阈值，不再硬编码 |

### 5.6 一个必须澄清的"看似矛盾"（本次已查清）

初次审计时我注意到：**原始数据里漏洞版中位 233 < 修复版中位 666**，
而**处理后漏洞版中位 251 < 修复版中位 535** —— 方向一致，**不矛盾**。

差异来自三处，我已逐条复现验证：

| 环节 | 影响 |
|------|------|
| 原始统计口径是"同时有两个代码字段的 9,983 条记录"，处理后是"18,925 条样本"（含只有单边字段的记录） | 中位从 233 → 254 |
| 划分后训练集（15,147 条）是全集（18,925 条）的子集 | 254 → 251 |
| 20,000 字符截断改变了长尾形状 | 546 → 535 |

**复现验证**：我用脚本完整重跑了「展开 → 长度过滤 → 截断 → MD5 去重」，
得到 `漏洞版中位 254 / 修复版中位 546`，与处理后文件的 `251 / 535` 吻合。

**所以结论是**：**"漏洞版更短"这个构造偏置在原始数据和处理后数据里都成立**，
图 7 的箱线图是正确的。

### 5.7 做得好的地方（必须肯定）

| 设计 | 实测证据 |
|------|----------|
| **按分组键划分** | 训练/验证/测试的交叉 = **0 / 0 / 0**，MD5 交叉 = **0** ✅ |
| **统一换行符** | 保证跨平台 MD5 一致，去重才能生效 |
| **规范化无效类型值** | 正确识别 6 种写法（含 `NVD-CWE-noinfo` / `NVD-CWE-Other` / `nan`） |
| **落盘前做一致性统计** | `cvefixes_stats.json` 记录每集合的样本数与标签分布，便于回归验证 |
| **流程可复现** | 独立脚本重跑得到完全一致的数字（18,925 / 15,147 / 1,876 / 1,902） |

### 6.3 设计说明（几个值得注意的实现细节）

**① 流式读 parquet，不一次性载入内存**

```python
pf = pq.ParquetFile(fp)
for batch in pf.iter_batches(batch_size=64, columns=cols):
    for row in batch.to_pylist():
        ...
```
CVEfixes 单个 parquet 有 400~550 MB，且个别代码字段达 55 MB，
`pq.read_table()` 全表解压后可能几 GB，容易内存溢出。

**② 缺失检查要同时查三种情况**

```python
if v is None:                     miss["null"] += 1
elif isinstance(v, str):
    if v.strip() == "":           miss["empty_str"] += 1
    elif v.strip().lower() == "nan": miss["nan_str"] += 1
```
只查 `isna()` 会漏掉 2,911 条空字符串和 4,799 条 `"nan"`。

**③ 长度类图表一律用对数轴**

因为分布右偏 5 个数量级（中位 233 vs 最大 55,330,596），
线性轴下所有信息都会挤在左边一个像素里。

**④ 字符/词元比运行期实测，不硬编码**

```python
CHARS_FOR_512 = int(MAX_LENGTH * measured_ratio)   # 实测 2.28 → 1168
```
这是本报告 §5.5 那个 40% 偏差的直接修复。

**⑤ 中文显示与版本兼容**

```python
matplotlib.rcParams["font.sans-serif"] = ["Microsoft YaHei", "SimHei", "SimSun"]
matplotlib.rcParams["axes.unicode_minus"] = False
```
另外 matplotlib ≥ 3.9 把 `boxplot()` 的 `labels` 参数改名为 `tick_labels`，
脚本里做了 try/except 双向兼容。

**⑥ 每次运行先清空旧图**

```python
for p in FIG_DIR.glob("*.png"):
    p.unlink()
```
避免改了脚本之后旧图还留在目录里、被误当成新结果。

## 一句话总结

> **这套预处理流水线的工程实现是合格的** —— 按分组键划分做到了零泄漏（这是最关键的决策），
> MD5 去重剔除了 10% 的重复，跨平台可完全复现（18,925 / 15,147 / 1,876 / 1,902 逐条一致）。
>
> **但数据本身和评测口径有四个必须正视的问题**：
> ① 原始数据的代码字段有 55 MB 级别的脏值、26% 的空值、**三套不同的缺失表示法**；
> ② 约 **27%** 的样本超过模型窗口，"头尾截断"的设计在这些样本上**实际失效**；
> ③ 测试集 **87.8%** 是"同一提交的漏洞版/修复版"同胞对，
>    而真正能代表"发现新漏洞"能力的孤立样本只有 **232 条、漏洞占比 7.76%**；
> ④ 用经验值（3.8 字符/词元）估算长度会让超窗比例**低估 40%** ——
>    凡是能实测的，不要用经验值。
>
> **换句话说：数据处理做对了，但用来衡量它的那把尺子是歪的。**
