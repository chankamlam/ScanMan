> 本文回答六个问题：**原始数据每条的字段 → 文本清洗规则 → 清洗后的结果 → 模型的输入 → 训练方式 → 推理输出**。
>
> 本文描述 ScanMan 项目（`src/` + `scripts/`）。文中所有结论都来自实际读代码 + 实际运行，
> 输出为历史实测结果；当前支持范围以根目录 [`../README.md`](../README.md) 为准，
> 全部命令与参数见 [`./09_命令参考.md`](./09_命令参考.md)。
> 文中少数"教学版（`vuln_bert_教学版/`）"的对照来自更早的独立教学项目，**该目录已不在本仓库**，
> 只作历史参考，不影响当前代码。
>
> 生成环境：Windows / Python 3.12 / torch 2.14.0（cu130 或 cpu）/ transformers 5.x。

## 0. 一句话总览

| 环节 | 输入 | 做什么 | 输出 |
|------|------|--------|------|
| 原始数据 | 4 个公开漏洞数据集的 parquet / jsonl | — | `data/raw/`，四源齐全约 2.2 GB；**只放 CVEfixes 时约 1.2 GB** |
| 数据清洗 | 原始记录 | 归一化 → 过滤 → 截断 → 去重 → 分组划分 | `data/processed/*.jsonl`，1.9 GB |
| 模型输入 | 一条 `code` 字符串 | 字符截断 → tokenize → padding | `input_ids` / `attention_mask` / `labels` |
| 训练 | 张量 + 标签 | CodeBERT 全参数微调 + 线性分类头 | `best/pytorch_model.bin`（约 500 MB） |
| 推理 | 一段源码 | 同样的预处理 → 前向 → softmax → argmax | `vulnerable`/`safe` 或 `CWE-xxx` + 置信度 |

两个任务：

| 任务 | 类型 | 输入 | 输出 | 类别数 |
|------|------|------|------|--------|
| **漏洞检测** | 二分类 | 一段源码（可能是安全代码，也可能有漏洞） | `safe` / `vulnerable` + 概率 | 2 |
| **漏洞分类** | 多分类 | 一段**已知有漏洞**的源码 | CWE 类型 + Top-5 候选 | 41（40 个 CWE + OTHER） |

## 1. 原始数据：每条样本包含什么

### 1.1 数据源

| 数据源 | 论文 | 原始规模 | 磁盘 | 本地路径 |
|--------|------|----------|------|----------|
| **CVEfixes** ⭐ | MSR 2021 | 13,000 条 CVE 修复记录 | 约 1.2 GB | `data/raw/cvefixes/train-00000-of-00003.parquet`（共 3 个分片） |

CVEfixes 的元信息在其中是最丰富的（23 个字段）。

> **关键**：CVEfixes 的标签不是单独一列，而是**从两个代码字段推出来的**——
> `vulnerable_code` → label 1，`fixed_code` → label 0。一条原始记录产出两条训练样本。

### 1.3 真实样本速览

```python
# CVEfixes
{'cve_id': 'CVE-2024-24746', 'cwe_id': 'CWE-835', 'language': 'C',
 'vulnerable_code': '    ble_npl_time_t now;\n    int32_t next_exp_in;…',
 'fixed_code': '    ble_npl_time_t now = ble_npl_time_get();…'}
```

### 1.4 三个容易踩的坑

1. **一条 CVE 记录产出两条样本，但两者不能分到不同 split。**
   `vulnerable_code` 与 `fixed_code` 往往只差几行，靠 `group_id = "cvefixes::<cve_id>::<hash>"`
   保证它们始终待在同一个 split，否则测试集会混进训练集的近似副本，F1 会虚高。
2. **安全样本没有 CWE。** 分类任务只用漏洞样本（7,291 条），检测任务的 18,925 条里
   有近一半不会出现在分类数据中，两个任务的样本数不是一回事。
3. **字符级截断与 token 级截断是两回事。** `data.max_code_chars: 20000` 做的头尾截断发生在构建阶段，
   而 tokenizer 的 `max_length: 512` 只保留**前** 512 个 token（约 1,800~2,000 字符），
   超长样本被保留的"尾部"可能根本进不了模型。详见 §4.2。

## 2. 文本清洗规则

清洗逻辑集中在 `scripts/build_dataset.py`，底层工具在 `src/utils.py`。**按执行顺序**共 8 步。

### 2.1 规则总览

| 步骤 | 函数 / 位置 | 做什么 | 为什么 |
|------|-------------|--------|--------|
| ① 字段归一化 | `build_cvefixes` | 原始字段映射成统一格式 | 原始字段名与训练格式不一致 |
| ② 代码清洗 | `_clean_code()` | 统一换行符 + 去首尾空白 | 换行符不统一会导致 MD5 去重失效 |
| ③ CWE 规范化 | `_norm_cwe()` | 统一成 `CWE-<数字>` | 同一类别可能写成 `79` / `cwe_79` / `CWE-79` |
| ④ 长度过滤 | `min_code_chars: 30` | 丢弃超短碎片 | 短于 30 字符基本没有语义 |
| ⑤ 头尾截断 | `truncate_code()` | 超 20,000 字符时保留头 60% + 尾 40% | 漏洞信息集中在函数头尾 |
| ⑥ MD5 去重 | `hashlib.md5(code)` | 相同代码只留一份 | CVEfixes 里 vuln/fixed 有时完全相同 |
| ⑦ 分组划分 | `split_groups()` | 按 `group_id` 分 8:1:1 | 防止修复前后代码泄漏到不同集合 |
| ⑧ 标签编码 | `prepare_task_data()` | CWE 字符串 → 0~40 编号，长尾合并 OTHER | 分类任务需要整数标签 |

### 2.2 逐条详解

#### ① 字段归一化：一条记录 → 一条或两条样本

**CVEfixes**（每个 CVE 产出 2 条，共用同一 `group_id`）：

```
vulnerable_code  →  id="<cve_id>-vuln",   label=1, cwe=<cwe_id>
fixed_code       →  id="<cve_id>-fixed",  label=0, cwe=""   ← 安全样本没有漏洞类型
project          =  repo_url 的最后一段（"https://github.com/apache/xxx" → "xxx"）
group_id         =  "cvefixes::<cve_id>::<hash>"
```

为什么不给 `fixed_code` 标 CWE：修复后的代码是**安全样本**，本身没有漏洞类型可言，
把它当成某个 CWE 的样本会污染分类任务的标签。因此分类任务只取 `vulnerable_code`。

另外，`fixed_code` 与对应的 `vulnerable_code` 构成一对天然的**难负样本**：
两者往往只差几行，模型必须分辨细粒度差异，而不是靠"这段代码看起来像不像有漏洞"来蒙。
这也是 CVEfixes 在检测任务上比随机采样的负样本更有价值的原因。

#### ② `_clean_code()` —— 真正意义上的"文本清洗"只有两条

```python
def _clean_code(code):
    if not isinstance(code, str):
        return ""                                     # 容错：非字符串一律当空
    return code.replace("\r\n", "\n").replace("\r", "\n").strip()
```

**就这两条**：统一换行符 + 去掉首尾空白。

| 不做的事 | 说明 |
|----------|------|
| 不删注释 | 注释里可能有关键线索（`/* TODO: check bounds */`） |
| 不压缩缩进 / 空白 | 缩进对 Python 是语法信息，不能动 |
| 不做语法解析 / AST | 保持纯文本，任何语言都能处理 |
| 不做大小写归一 | 标识符大小写有意义 |

> 统一换行符是**必需的**：不统一的话，同一段代码在 Windows（`\r\n`）和 Linux（`\n`）上
> 算出的 MD5 不同，去重会失效。

#### ③ `_norm_cwe()` —— 标签清洗

```
_norm_cwe("CWE-79")          → "CWE-79"
_norm_cwe("79")              → "CWE-79"
_norm_cwe("cwe_79")          → "CWE-79"
_norm_cwe("CWE-079")         → "CWE-79"     # int() 去掉前导零
_norm_cwe(None)              → ""
_norm_cwe("nan")             → ""
_norm_cwe("NVD-CWE-noinfo")  → ""           # "没查到"，当空处理
_norm_cwe("NVD-CWE-other")   → ""
```

不统一的话，同一个 CWE-79 会被模型当成好几个不同的类别。

#### ④ 长度过滤

```yaml
min_code_chars: 30    # 清洗后短于 30 字符的碎片直接丢弃
```

#### ⑤ 头尾截断 `truncate_code()`

```python
def truncate_code(code, max_chars=8000, head_ratio=0.6):
    if len(code) <= max_chars:
        return code
    head_len = int(max_chars * head_ratio)          # 60%
    tail_len = max_chars - head_len                 # 40%
    return code[:head_len] + "\n/* ... [中间代码已截断] ... */\n" + code[-tail_len:]
```

示例：

```
truncate_code("a"*100, max_chars=10, head_ratio=0.6)
→ 'aaaaaa\n/* ... [中间代码已截断] ... */\naaaa'
```

**为什么头尾都留：** 漏洞关键信息集中在两处——

- **函数头部**：参数声明、输入校验、缓冲区大小（`char buf[10]` 直接决定会不会溢出）
- **函数尾部**：返回值处理、内存释放（`free`/`close`）、错误分支、锁释放

只保留前 N 个字符会丢掉尾部的 `free()`，use-after-free / 资源泄漏类漏洞就判不出来了。

> ⚠️ **这个项目有两道字符截断**：
> 构建数据时用 `data.max_code_chars = 20000`；送进 tokenizer 前又用 `model.max_code_chars = 8000` 截一次。
> 改配置时两个都要看。

#### ⑥ MD5 去重

```python
hashlib.md5(code.encode("utf-8", errors="ignore")).hexdigest()
```

用 MD5 而不是 Python 内置 `hash()`，因为内置 hash 每次进程启动都加随机盐，无法跨运行去重。
`errors="ignore"` 保证遇到无法编码的字符也不崩。

#### ⑦ 按 `group_id` 分组划分（本项目最重要的设计）

```python
# 错误做法（很多教程这么写）
random.shuffle(records); train = records[:8000]      # ← 会数据泄漏！

# 正确做法
groups = 按 group_id 聚合(records)
random.Random(seed).shuffle(list(groups.keys()))     # 打乱的是"组"，不是"样本"
train = 展开(前 80% 的组); val = 展开(中间 10%); test = 展开(后 10%)
```

**不这么做的后果**：同一个 CVE 的两条样本只差一个函数名——

```c
char buf[10]; strcpy(buf, user_input);                   /* label=1 */
char buf[10]; strncpy(buf, user_input, sizeof(buf)-1);   /* label=0 */
```

随机划分会把它们拆到训练集和测试集两侧，模型在测试集上遇到的是**训练样本的近邻副本**，
指标虚高到 0.99，换到真实新漏洞上表现一塌糊涂。

#### ⑧ 分类任务：长尾合并

```python
pool = [r for r in records if r["label"] == 1 and r["cwe"]]   # 只要"有漏洞 + 有 CWE"
counter = Counter(r["cwe"] for r in pool)
kept = [(c, n) for c, n in counter.most_common() if n >= 30][:40]   # 频次≥30，最多取 40 个
cwe_to_id = {c: i for i, (c, _) in enumerate(kept)}
other_id  = len(cwe_to_id)                     # OTHER 排在最后
for r in pool:
    r["label"] = cwe_to_id.get(r["cwe"], other_id)
```

⚠️ **最终类别数 = 保留的 CWE 数 + 1**。这个 +1 很容易漏，
漏了 `CrossEntropyLoss` 会报 `weight tensor should be defined either for all N classes`。

### 2.3 清洗前 → 清洗后

| | 内容 |
|---|---|
| **原始一条** | CVEfixes parquet 中 `CVE-2024-24746` 的 `vulnerable_code` |
| | `'    ble_npl_time_t now;\r\n    int32_t next_exp_in;\r\n    uint16_t conn_handle;\r\n    for (;;) {\r\n…'`（2,655 字符，整行共 23 个字段） |
| **清洗后一条** | `{"id": "CVE-2024-24746-vuln", "code": "ble_npl_time_t now;\n    int32_t next_exp_in;…", "label": 1, "cwe": "CWE-835", "cwe_name": "Loop with Unreachable Exit Condition ('Infinite Loop')", "source": "cvefixes", "language": "C", "project": "mynewt-nimble", "group_id": "cvefixes::CVE-2024-24746::d42a0ebe…", "code_hash": "…"}` |
| **变化** | 23 个字段 → 10 个字段；`\r\n` → `\n`；首尾空白去掉；标签从两个代码列推导出来；多了 `group_id` / `code_hash` |

## 4. 模型需要的输入

### 4.1 从文本到张量的两级处理

```
JSONL 里的 code 字符串
        ↓ ① 字符级头尾截断（truncate_code，8000 字符）
        ↓ ② 分词（tokenizer，max_length=512）
┌──────────────────────────────────────────┐
│ input_ids       (B, L)    token 编号       │  ← 模型真正吃的
│ attention_mask  (B, L)    1=真实 0=padding │
│ labels          (B,)      标签（训练时）    │
└──────────────────────────────────────────┘
        ↓ 模型
      logits (B, K)
```

### 4.2 字符级头尾截断

送进 tokenizer 之前**又截一次**（默认 8000 字符，见 `configs/config.yaml` 的 `model.max_code_chars`）。

```
8000 字符 ≈ 2000~3000 个 token，能覆盖绝大多数函数
CodeBERT 的 token 上限是 512，所以最终还是要靠 tokenizer 的 truncation 收口
```

### 4.3 分词 —— 真实运行结果

输入 `void copy_input(char *user_input) { char buf[10]; strcpy(buf, user_input); }`：

```
切分后共 28 个 token：
['void', 'Ġcopy', '_', 'input', '(', 'char', 'Ġ*', 'user', '_', 'input', ')',
 'Ġ{', 'Ġchar', 'Ġbuf', '[', '10', '];', 'Ġstr', 'c', 'py', '(',
 'buf', ',', 'Ġuser', '_', 'input', ');', 'Ġ}']

对应编号：
[47908, 5375, 1215, 46797, 1640, 24262, 1009, 12105, 1215, 46797, 43, 25522,
 16224, 49125, 10975, 698, 44082, 7031, 438, 17163, 1640, 48939, 6, 3018,
 1215, 46797, 4397, 35524]
```

注意两点：

- `strcpy` 被切成了 `str` + `c` + `py` 三段（BPE 子词切分）
- `Ġ` 表示"这个 token 前面有一个空格"

### 4.4 模型真正吃的张量

> ⚠️ **下面这段只是为了看清张量长什么样，用的是固定补齐（`padding="max_length"`）；
> 真实管道是动态补齐**（`src/data.py:98` 里编码时 `padding=False`，再由
> `DynamicPaddingCollator` 调 `tokenizer.pad(padding=True, pad_to_multiple_of=8)`
> 补到**本 batch 最长**并对齐到 8 的倍数，见 §4.6 / §4.7）。
> 固定补到 512 会让短样本白算一大堆 `[PAD]`。

```python
# 仅示意，非实际管道
tokenizer(code, max_length=32, padding="max_length", truncation=True, return_tensors="pt")
```

实测输出：

```
input_ids      : [[0, 47908, 5375, …, 35524, 2, 1, 1]]
attention_mask : [[1, 1, 1, …, 1, 1, 1, 0, 0]]

解码回文本：<s>void copy_input(char *user_input) { char buf[10]; strcpy(buf, user_input); }</s><pad><pad>
```

| 特殊符号 | 编号 | 含义 |
|----------|-----:|------|
| `<s>` | 0 | 句子起始标记（相当于 BERT 的 `[CLS]`），**它的输出向量用来做整句分类** |
| `</s>` | 2 | 句子结束标记（相当于 `[SEP]`） |
| `<pad>` | 1 | 补齐用的填充符，`attention_mask` 里为 0 的位置就是它 |

> CodeBERT 是 **RoBERTa 系**分词器（BPE），所以是 `<s>/</s>`；
> 如果换成 `bert-base-uncased` 这类原生 BERT，则是 `[CLS]/[SEP]`，而且会多输出一个 `token_type_ids`。

### 4.5 `token_type_ids` 的坑

```python
# 工程版 src/models.py
self.accepts_token_type_ids = getattr(hf_config, "type_vocab_size", 0) > 1
# 前向传播时
if not self.accepts_token_type_ids:
    token_type_ids = None
```

CodeBERT / UniXcoder 是 RoBERTa 系，**没有"句子A/句子B"的概念，不接受 `token_type_ids`**，
硬传进去会报 `TypeError`。模型类自动探测一次，推理脚本也做了过滤。

### 4.6 动态 padding（关键优化）

不统一补齐到 512，而是**补到本 batch 最长的那条**，并且对齐到 8 的倍数（GPU Tensor Core 友好）。

```
假设 batch 内有 3 条样本，长度分别是 40 / 120 / 800：

固定 padding 到 512  →  3 × 512 = 1536 个位置的计算量
动态 padding 到 808  →  约 808 个位置的计算量
```

代码数据集长短差异极大，实测提速 2~3 倍。代价是每个 batch 的 `L` 不同，无法预先生成固定形状的输入。

### 4.7 输入处理要点

| 维度 | ScanMan 的实现 |
|------|----------------|
| 预处理位置 | `src/data.py::VulnDataset.__getitem__` |
| 字符级头尾截断 | ✅ `truncate_code(code, model.max_code_chars)` |
| padding 方式 | **动态**，补到本 batch 最长（对齐 8） |
| `max_length` | 512（`configs/config.yaml`） |
| 采样时机 | `__getitem__` 里逐条按需分词 |
| 内存占用 | 逐条读取，不一次性把整个训练集载入内存 |

## 5. 模型的训练方式

### 5.1 模型结构

```
input_ids (B, L)
    ↓
┌──────────────────────────────┐
│  CodeBERT 编码器               │  124M 参数，预训练权重，微调时全参数更新
│  (12 层 Transformer)           │
└──────────────────────────────┘
    ↓ last_hidden_state (B, L, 768)
┌──────────────────────────────┐
│  池化 Pooling                  │  取 [CLS]（第 0 个位置）向量
└──────────────────────────────┘
    ↓ (B, 768)
┌──────────────────────────────┐
│  Dropout(0.1)                 │  训练时随机丢弃 10% 神经元
└──────────────────────────────┘
    ↓
┌──────────────────────────────┐
│  Linear(768, K)               │  随机初始化，K=2（检测）或 41（分类）
└──────────────────────────────┘
    ↓
logits (B, K)   ← 未归一化，直接交给 CrossEntropyLoss
```

代码位置：`src/models.py::VulnClassifier`。

**为什么用 `AutoModel` 而不是 `AutoModelForSequenceClassification`：**
一是要自己控制分类头结构（Dropout 位置、池化方式），二是 `AutoModel` 更通用，
CodeBERT / GraphCodeBERT / UniXcoder 都能加载。

**分类头初始化**：均值 0、标准差 0.02 的正态分布（BERT 原论文做法，与预训练权重的量级匹配）。

**实测参数量**：检测 124.6M（总计 = 可训练，没有冻结任何层）；分类 124.7M。

### 5.2 损失函数与类别不平衡

`nn.CrossEntropyLoss`（内部 = log_softmax + NLLLoss，所以传进去的必须是**未归一化的 logits**）。

三种不平衡策略（`data.imbalance`）：

| 策略 | 做法 | 适用 |
|------|------|------|
| `none` | 不做处理 | 数据均衡时 |
| **`weighted_loss`（默认）** | 加权交叉熵，`weight[i] = N / (K × n_i)` | 推荐。所有样本都参与训练，只是少数类的损失被放大 |
| `balanced_sampler` | `WeightedRandomSampler`，少数类被更频繁抽到 | 备选。两者别同时用，会过度补偿 |

实测权重（CVEfixes 检测，64 条调试样本）：`[0.762, 1.455]`——漏洞类的损失被放大近 2 倍。

### 5.3 优化器与分层学习率

```python
AdamW(betas=(0.9, 0.999), eps=1e-8)

参数组 1：编码器所有权重             lr = 2e-5   weight_decay = 0.01
参数组 2：编码器的 bias / LayerNorm   lr = 2e-5   weight_decay = 0.0
参数组 3：分类头                     lr = 1e-4   weight_decay = 0.01   ← 大 5 倍
```

**为什么分类头学习率更大：** 编码器是"预训练好的、已经很好"的，只需小幅微调；
分类头是随机初始化的，一开始输出全是噪声，需要更大的步长才能收敛。

**为什么 bias / LayerNorm 不做 weight decay：** 权重衰减会把参数往 0 拉，
但 bias 和 LayerNorm 的缩放参数本来就该接近 1，强行拉向 0 反而损害表达能力。这是 BERT 微调的通行做法。

### 5.4 学习率调度

`get_linear_schedule_with_warmup`，先升后降：

```
lr
 │      ╱‾‾‾‾‾‾╲
 │    ╱           ╲
 │  ╱               ╲___
 └──────────────────────→ step
  ↑ 预热 10%  ↑   线性衰减到 0
```

预训练权重已经很好，一上来就用大学习率会"冲坏"它们，所以前 10% 的步数从 0 线性升到目标值。

### 5.5 训练循环（手写，不用 transformers 的 Trainer）

```python
# ============ 4 个准备 ============
train_loader, val_loader, test_loader = build_dataloaders()   # 准备数据
model = VulnClassifier(...)                                    # 准备模型
criterion = nn.CrossEntropyLoss(weight=...)                    # 准备损失函数
optimizer, scheduler = build_optimizer_scheduler(...)          # 准备优化器

# ============ 2 个遍历 ============
for epoch in range(1, epochs + 1):                 # 外层：轮次
    model.train()
    optimizer.zero_grad(set_to_none=True)
    for step, batch in enumerate(train_loader):    # 内层：批次
        # ============ 5 个核心 ============
        logits = model(**inputs)                       # ① 前向传播
        loss = criterion(logits, labels) / accum       # ② 计算损失（梯度累积要缩放）
        optimizer.zero_grad(set_to_none=True)          # ③ 梯度清零
        loss.backward()                                # ④ 反向传播
        clip_grad_norm_(model.parameters(), 1.0)       #    梯度裁剪
        optimizer.step(); scheduler.step()             # ⑤ 参数更新

    # ============ 1 个保存 ============
    val_metrics, val_score, _, _ = evaluate(model, val_loader)
    if val_score > best_score:
        torch.save(model.state_dict(), best_dir / "pytorch_model.bin")
```

**梯度累积**：`loss = loss / accum` 缩小后再反传，累积 `accum` 个 batch 后梯度刚好等于一次大 batch。
`batch_size=4 + accum=4` ≡ `batch_size=16`，但显存只占 1/4。

**混合精度（AMP）**：GPU 上 `auto` 会优先选 bf16（动态范围大，不需要 GradScaler），
不支持则 fp16；CPU / MPS 自动关闭。实测日志显示 `精度=no`（因为在 CPU 上跑）。

### 5.7 早停与模型选择

```python
best_score, best_epoch, patience = -1.0, -1, 0
for epoch in ...:
    train_loss = train_one_epoch(...)
    val_metrics, val_score, _, _ = evaluate(model, val_loader, ...)
    if val_score > best_score:            # ← 看的是"验证集"，不是训练集
        best_score, best_epoch, patience = val_score, epoch, 0
        torch.save(model.state_dict(), best_dir / "pytorch_model.bin")
        tokenizer.save_pretrained(best_dir)
        save_label_map(best_dir)
    else:
        patience += 1
        if patience >= patience_limit:
            break

# 训练结束后：加载"验证集最优"的权重，而不是最后一轮的
model.load_state_dict(torch.load(best_dir / "pytorch_model.bin"))
evaluate(model, test_loader, ...)
```

|------|--------|----------|
| detection | **F1** | accuracy / precision / recall / f1 / mcc / roc_auc / pr_auc / tn / fp / fn / tp |

对漏洞检测来说 **FN 比 FP 严重得多**：漏掉一个真漏洞可能被利用，误报只是让开发者多看一眼。

```
    ├── tokenizer.json       ← 分词器（必须与训练时一致）
    ├── tokenizer_config.json
    └── label_map.json       ← 任务类型 + 类别数 + id2name
```

推理器 `VulnPredictor.__init__` 的加载顺序：
读 `label_map.json` 确定 `num_labels` → 读 `config.yaml` 确定 `base_model` 和 `max_length`
→ 从检查点目录加载 tokenizer → 建 `VulnClassifier` → `load_state_dict` → `eval()`。

**`num_labels` 必须与训练时一致**，否则 `load_state_dict` 会因为形状不匹配而报错。

### 8.2 指标预期（别被数字骗了）

| 场景 | 合理的 F1 | 本仓库实测 |
|------|-----------|-----------|
| CVEfixes（"修复前后对比"数据） | 0.75 ~ 0.85 | **0.7521**（3 轮，未收敛） |
| 合并数据检测（`merged_detection_codebert`） | 与 CVEfixes 不可直接比（正例率低） | F1 0.4848 / ROC-AUC 0.8717（阈值 0.5） |
| （参考文献量级）跨数据集 / 真实分布，如 BigVul / Devign | 0.25 ~ 0.65 | 跨源评估明显低于分布内，属公开难题 |
| 分类任务（28 类） | 长尾类别会明显拉低 macro-F1，要同时看 Top-5 | Macro-F1 0.2392 / Top-5 0.7438 |

**如果 CVEfixes 的 F1 到了 0.99**，先检查是不是划分方式错了
（按样本随机分而不是按 `group_id` 分组分）。

**如果 F1 在 0.75 左右**，先别急着调模型——按下面的顺序排查：

1. **轮数够不够**：看 `results.json` 里 val F1 是否还在涨、train_loss 是否还在降。
   还在涨就说明是"训练不足"，加轮数即可（本项目实测就是这种情况）。
2. **阈值合不合适**：默认 0.5。漏洞检测场景漏报比误报严重，降到 0.3 能让漏报减少约 40%
   （见下表），而 F1 几乎不变。
3. **数据是否够**：`--max-train-samples` 有没有误设。

#### 阈值对结果的影响（同一个模型，只改判定阈值）

| 阈值 | precision | recall | F1 | 漏报 FN | 误报 FP |
|-----:|----------:|-------:|---:|--------:|--------:|
| 0.20 | 0.6392 | 0.9179 | 0.7536 | 70 | 442 |
| **0.30** | 0.6577 | 0.8851 | **0.7546** | 98 | 393 |
| 0.40 | 0.6802 | 0.8429 | 0.7529 | 134 | 338 |
| **0.50（默认）** | 0.7053 | 0.8054 | 0.7521 | 166 | 287 |
| 0.60 | 0.7300 | 0.7292 | 0.7296 | 231 | 230 |
| 0.70 | 0.7721 | 0.6354 | 0.6971 | 311 | 160 |

阈值从 0.5 降到 0.3：**漏报从 166 降到 98（-41%），F1 反而略升**。
如果只要求 precision ≥ 0.6，阈值取 0.12 能把 recall 拉到 **0.9543**（漏报只剩 39 条）。

上表来自 `outputs/cvefixes_detection_codebert-base/` 的 `probs_test.npy` 扫阈值所得。

> ⚠️ 那份 `.npy` **现在已经不在了**。`.gitignore` 把 `outputs/*/*.npy` 排除在版本库外，
> 未随仓库分发，所以那段数据加载不了。
>
> 要看现值，用**带 `.npy` 的 run**（例如 `outputs/merged_detection_codebert/`），
> 或者直接跑 `scripts/tune_threshold.py --run outputs/<run> --split val --criterion f1 --write`，
> 它会自己读取 `probs_val.npy` / `labels_val.npy` 并按 F1 扫出阈值。

## 附录 B：术语表

| 术语 | 含义 |
|------|------|
| **CWE** | Common Weakness Enumeration，软件弱点分类标准（`CWE-79` = XSS） |
| **CVE** | Common Vulnerabilities and Exposures，单个漏洞的编号 |
| **CodeBERT** | 微软在 CodeSearchNet 6 种语言上预训练的代码 BERT，125M 参数 |
| **token** | 分词器切出的最小单位，一个 token 不等于一个单词 |
| **logits** | 模型输出的未归一化分数，softmax 之后才是概率 |
| **`group_id`** | 防泄漏分组键（CVE + commit hash），同一组的所有样本必须在同一个 split |
| **难负样本** | 与正样本只差几行的负样本（如 CVEfixes 里与 `vulnerable_code` 配对的 `fixed_code`），逼迫模型学细粒度差异 |
| **macro-F1** | 每一类分别算 F1 再取平均，类别等权，长尾类别影响大 |
| **weighted-F1** | 按类别样本量加权平均，样本多的类别影响大 |
| **warmup** | 训练初期把学习率从 0 线性升到目标值，避免破坏预训练权重 |
| **梯度累积** | 多个 batch 的梯度累加后再更新一次参数，等效于大 batch，省显存 |
| **AMP** | Automatic Mixed Precision，混合精度训练，显存减半、速度提升约 30% |
| **动态 padding** | 补到本 batch 最长，而不是补到全局最大长度 |
