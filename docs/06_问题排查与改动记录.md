### 问题 1 — 搞懂项目全貌

**原始提问**：数据集里每条样本包含哪些内容？文本清洗的规则是什么？得到的结果是什么？
模型需要的输入是什么？模型的训练方式是什么？给模型一个输入得到的输出是什么？

**结论**：

| 问题 | 答案落点 |
|------|----------|
| 每条样本有什么 | CVEfixes 23 个字段（含 `vulnerable_code` / `fixed_code` / `cwe_id` / diff / 评分）；BigVul 11 个；DiverseVul 5 个；CodeXGLUE 5 个 |

| 清洗后结果 | 统一 11 字段 JSONL；CVEfixes 检测 18,925 条、分类 7,291 条(41 类) |
| 模型输入 | `input_ids` / `attention_mask` / `labels`，`max_length=512`，动态 padding |
| 训练方式 | CodeBERT 全参微调 + 线性分类头，加权交叉熵，分层学习率 2e-5 / 1e-4，warmup 10% |
| 输出 | 检测：`safe`/`vulnerable` + 概率；分类：`CWE-xxx` + Top-5 |

**产出**：`docs/01_数据集与模型全解析.md`

### 问题 6 — 为什么四个数据集不能融合？能不能找新数据集让它均衡？

**结论一：融合不是"不能"，代码里已经实现了**（`--source merged`，数据也生成好了）。
问题是**融了之后会变成什么样**：

| 副作用 | 实测数据 |
|--------|----------|
| **① 不均衡恶化** | CVEfixes 44.5% 正例 → 融合后 **9.7%**；不均衡比 1.25:1 → **9.29:1** |
| **② 数据被大量去重** | 581,506 → 429,308，**26.2% 是重复**；CodeXGLUE 21,803 条**只剩 95 条** |
| **③ 源权重失衡** | DiverseVul 64.5% + BigVul 32.0% = 96.5%，**CVEfixes 只剩 3.5%** |
| **④ 跨源泄漏** | 测试集 **1.4%**（747 条）能在训练集找到明显重复代码 |
| **⑤ 语言分布扭曲** | CVEfixes 是多语言，另三个是纯 C/C++ |

根本原因：**数据量最大的两个源恰好最不均衡**。BigVul ∩ DiverseVul 有 102,500 条完全相同的代码
（DiverseVul 本来就是从 BigVul 用过的项目重新爬的）。

**结论二："找新数据集解决不均衡"方向是错的。**

不均衡不是数据集选得不好，**是漏洞检测任务的本质**——真实世界里漏洞函数天然是少数
（BigVul 5.2%、DiverseVul 8.1%）。任何从真实 CVE 修复提交抽取的数据集都会是这个量级。

那为什么现有数据是 44.5% 均衡的？因为 **CVEfixes 和 CodeXGLUE 的构造方式是特例**：
CVEfixes 是"漏洞版本 vs 修复版本"成对抽取（天然 1:1），CodeXGLUE 是人工标注时特意平衡过。

**已经有的这两个恰好就是均衡的那两个。**

### 问题 7 — 只用 CVEfixes 样本够吗？训练集里是不是混进了测试集数据？

#### 7.1 数据泄漏检查（六层）

| 检查项 | 结果 | 判定 |
|--------|------|------|
| `group_id` 跨 split | **0 条** | ✅ 分组划分正确 |
| `code_hash`（完全相同） | **0 条** | ✅ MD5 去重生效 |
| 去空白指纹（只差缩进） | 6 条（测试集 0.3%） | 轻微 |
| **同一个 CVE 跨 split** | **96 个 CVE / 180 条测试样本（9.5%）** | ⚠️ **结构性缺陷** |
| 5-gram 相似度 > 0.80 | 13 条（0.68%） | 近乎重复的极少 |
| 5-gram 相似度 > 0.50 | 38 条（2.0%） | 轻微 |

**根因**：`group_id` 用的是 `cvefixes::<cve_id>::<hash>`（CVE + commit），
而**一个 CVE 可能有多个修复提交** → 每个 commit 一个 group → 被划分拆开。

**决定性验证**：

| | 数量 |
|---|---:|
| CVE 总数 | 9,958 |
| 涉及多个 commit 的 CVE | 517 |
| 跨 split 的 CVE | **195** |
| 其中"本身有多个 commit"导致的 | **195 / 195 = 100%** |
| 只有一个 commit 的 CVE | 9,441，**跨 split 的 0 个** |

#### 7.2 泄漏对成绩的影响：几乎为零

把测试集按"CVE 是否在训练集出现过"拆成两组，分别算指标：

| 组 | 样本数 | precision | recall | F1 | ROC-AUC |
|---|---:|---:|---:|---:|---:|
| A 组：CVE 在训练集出现过 | 180（9.5%） | 0.6129 | 0.9500 | 0.7451 | 0.8262 |
| B 组：CVE 训练集没见过 | 1,722（90.5%） | 0.6242 | 0.9392 | **0.7500** | **0.8452** |
| 全体 | 1,902 | 0.6232 | 0.9402 | 0.7495 | 0.8432 |

**A 组（有重叠的）表现不但没更好，反而略差。** 把 A 组整个剔除后
F1 0.7495 → 0.7500、ROC-AUC 0.8432 → 0.8452，**基本不变**。

**结论：不需要因为泄漏重新训练。F1 = 0.75 / 召回率 0.94 是可信的。**

#### 7.3 样本量够不够？学习曲线实测

固定超参和随机种子，只改 `--max-train-samples`：

| 数据量 | 训练样本 | test F1 | test MCC | test ROC-AUC | test PR-AUC | 最佳轮次 |
|--------|---------:|--------:|---------:|-------------:|------------:|---------:|
| 25% | 3,787 | 0.7185 | 0.4417 | 0.7829 | 0.7160 | 4（早停） |
| 50% | 7,573 | 0.7211 | 0.4520 | 0.7958 | 0.7316 | 2（早停） |
| **100%** | **15,147** | **0.7490** | **0.5305** | **0.8432** | **0.7817** | 4 |

**三个指标全部单调上升 → 数据没饱和。** 对数线性拟合：**数据每翻一倍约 +1.5 F1 点 / +3.0 ROC-AUC 点**
（推算 30k → F1 ≈ 0.765；60k → F1 ≈ 0.78）。

| 问题 | 回答 |
|------|------|
| 15,147 条够训出可用模型吗？ | ✅ 够，能到 F1 0.75 / 召回率 0.94 |
| 饱和了吗？ | ❌ 没有，100% 仍最优 |
| 扩数据有用吗？ | ✅ 有用，但边际递减：翻倍 ≈ +1.5 F1 点 |
| 靠融合四源扩数据？ | ❌ 不该，正例率会被稀释到 9.7% |
| 那怎么扩？ | 优先"同分布扩容" |

### 问题 9 — "把整个项目丢给模型，数出每个文件有几个函数有漏洞"（2026-09-19）

**原始提问**：模型的输入是函数级还是文件级？我想把整个项目文件丢给模型，
让它判断每个文件里有多少 function 有漏洞，后续还要加漏洞分类。

**结论**：模型的池化方式是 **[CLS]**（`src/models.py:174`），一次前向只对
**一段代码**输出**一个**结论 —— 它自己**答不了**"这个文件里几个函数有漏洞"。
所以必须外部聚合：**抽函数 → 逐函数推理 → 按文件统计**。而函数抽取这一步
**从来没实现过**（`build_dataset.py` 用的是 HF 上下载的现成片段，不是自己抽的）。

**本次做了两件事**：① 实现函数抽取 + 扫描链路；② 分类**只出设计方案**，不写代码。

**用户拍板**：抽取支持主流 4 语言族（C/C++、Python、JS/TS、PHP），留注册表扩展；
分类本期只讨论设计。

#### 9.1 交付物

见 [2.1 新增文件](#21-新增文件) 的 `src/extract.py` / `scripts/scan_project.py` /
`scripts/spike_align.py` / `tests/` / `docs/07`。

#### 9.2 ⚠️ 本次最大的坑：tree-sitter 读 `.row` 会**非确定性段错误**

**这是整个排查里最值得记的一件事**，现象和结论如下。

**现象**：`src/extract.py` 抽取时**随机**崩溃（access violation，退出码 139）。
"随机"是关键：**同一份代码、同一批输入，三次运行崩在三个不同的文件/行上**。
`threading.stack_size` 加大到 512 MB 也一样。

**排查过程中被**排除**的假设**（都是先怀疑、用实验否掉的）：

| 假设 | 否掉的方式 |
|------|-----------|
| `Language` 对象被 GC 掉了 | 持有强引用（模块级变量）后照样崩 |
| Python 侧 `Tree` 被 GC | 同上 |
| 递归太深 / 爆栈 | 加大栈后实测 `_walk` 只有 3 层、最大深度 22，**不是栈溢出** |
| `Parser` 被 `lru_cache` 复用出问题 | 每次新建 Parser 照样崩 |
| ABI 版本不匹配 | ABI 验证脚本全绿（见 9.4） |
| 语法树损坏 | 崩溃点与树的内容无关，换输入崩溃点也换 |
| `__pycache__` 陈旧 | 清掉后照样崩 |

**定位过程**：写了一个**完全不经过 `src/extract.py`** 的纯 tree-sitter 最小复现
（逐项触碰节点 API：`type` / `start_byte` / `end_byte` / `child_count` / `has_error` /
`child_by_field_name` / `start_point` / `end_point`），才锁定了元凶：

| 触碰的 API | 结果 |
|-----------|------|
| `node.type`、`start_byte`、`end_byte`、`child_count`、`has_error` | ✅ 安全 |
| `node.child_by_field_name(...)` | ✅ 安全 |
| `node.start_point` / `node.end_point` **对象本身** | ✅ 安全 |
| `node.start_point.column` | ✅ 安全 |
| **`node.start_point.row` / `node.end_point.row`** | ❌ **段错误** |

**结论**：本机环境（py312 + tree-sitter 0.26.0 + tree-sitter-python 0.25.0）下，
**只有 `.row` 会崩**，属于**绑定层缺陷，与本项目代码无关**。换个版本的
tree-sitter 可能不复现 —— 但既然踩到了，就当它一直存在。

**最小复现**（6 行，想自己确认的话直接跑）：

```python
import tree_sitter_python
from tree_sitter import Language, Parser

p = Parser(Language(tree_sitter_python.language()))
n = p.parse(b"def f(): pass\n").root_node.children[0]
print(n.type)                 # ✅ 安全
print(n.start_point.column)   # ✅ 安全
print(n.start_point.row)      # 💥 段错误（非确定性）
```

**修复**：行号**一律由字节偏移推导**（数 `\n` + `bisect`），彻底不碰
`start_point` / `end_point`。附带好处有两条：

1. 与 tree-sitter 版本**解耦**，升级不会突然崩；
2. 语义与 `point.row + 1` **严格一致**（行同样以 `\n` 分隔），
   且顺带避开了 `column` 那个坑 —— 它是**行内字节偏移**，有中文注释时
   和编辑器的字符列号对不上。

**防回归**：`tests/test_extract.py::test_no_point_api_usage` 用 AST 遍历
（不是文本匹配，这样文档里可以放心继续写这个坑）断言 `src/extract.py` 里
**不存在** `start_point` / `end_point` 属性访问。

#### 9.3 另一半：训练数据与真实输入**不是同一个分布**

`build_dataset.py` 喂给模型的不是函数，而是 CVE 修复 diff 里**被删除行的拼接**
（碎片）。而扫描真实项目抽的是**完整函数**。本次用 `scripts/spike_align.py`
把它量了出来，完整数据见 [`docs/07` 第六节](./07_漏洞分类设计方案.md#六战略根治训练数据与真实输入不是同一个分布)，
结论摘要：

| | 训练碎片 | 真实项目函数 |
|---|---:|---:|
| 长度中位数 | 384 字符 | 591 字符（1.54×） |
| 完全无函数签名 | 89.6% | **0.0%** |
| 以签名开头 | 5.1% | 95.7% |

三组 F1（阈值 0.11）：测试集全体 0.7495 / 其中含签名子集 0.7500 /
**人工手写完整函数 0.6667**（n=20）。按**事先写死**的判定规则
（F1 落差 > 15 点 或 组 C 召回率 < 0.5）判定为"漂移未达实质性门槛"。

> ⚠️ **但这个"通过"不是绿灯**：同一检查点、同一阈值扫本仓库自己的 `src/`
> （47 个纯函数，`_name_of`、`__len__` 这种），**31.9% 被判为可疑**。
> 详见 [`docs/07` 6.5](./07_漏洞分类设计方案.md#65-反过来看为什么这个通过不能当成绿灯)。
