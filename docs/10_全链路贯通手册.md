这个函数做了什么变换、数据从什么样子变成了什么样子。

## 0. 总览：这是两条独立的链路

```text
【训练链路】离线跑一次，产出模型
  data/raw/*.parquet
      │ build_dataset.py          抽字段、拆正负样本、清洗、去重、划分
      ▼
  data/processed/*.jsonl           文本 + 标签
      │ data.py + models.py        分词、张量化
      ▼
  train.py                         AdamW 微调 CodeBERT
      ▼
  outputs/<run>/best/              模型权重 + 标签映射 + 阈值

【推理链路】每次扫描/上传都跑
  浏览器选文件
      │ api.ts                    读原始字节 → base64
      ▼
  serve.py                        HTTP 校验 → 落盘到临时目录
      │ scan_project.py           遍历文件、调下面两个
      ▼
  extract.py                      tree-sitter 切函数（完整函数）
      │ predict.py                分词 → 前向 → softmax → 阈值判定
      ▼
  scan_project.py                 命中函数再跑分类 → 汇总报告
      │
      ▼
  浏览器渲染
```

**关键差别**：训练吃的是 **CVE 修复 diff 的补丁块**（常常是函数中间一段），
推理吃的是 **tree-sitter 抽出来的完整函数**。两者不是一个分布 —— 详见第 3 部分。

# 第一部分 · 训练链路

## 1 · 原始数据长什么样

**文件**：`data/raw/cvefixes/train-0000{0,1,2}-of-00003.parquet`（3 个分片，合计约 1.16 GB）

每行 = 一条 CVE 修复记录，**23 列**。真正被用到的只有 8 列：

| 列 | 样例 | 用途 |
|---|---|---|
| `cve_id` | `CVE-2024-24746` | 样本 id 前缀 |
| `hash` | `d42a0ebe...` | 修复提交的 commit hash |
| `repo_url` | `https://github.com/apache/mynewt-nimble` | 取最后一段当 `project` |
| `cwe_id` | `CWE-835` | 分类标签 |
| `cwe_name` | `Loop with Unreachable Exit Condition ('Infinite Loop')` | 展示用 |
| `language` | `C` | 语言标记（**注意：模型不按语言分流，见 §14**） |
| `vulnerable_code` | 修复前的代码块 | → **label = 1** |
| `fixed_code` | 修复后的代码块 | → **label = 0** |

> 其余 15 列（`diff_with_context`、`cvss3_base_score`、`severity` 等）**不读**。
> `build_cvefixes` 显式写死列名列表，就是为了不把超长的 `diff_with_context` 读进内存。

## 2 · 一条记录拆成两条样本

**函数**：`scripts/build_dataset.py:209` `build_cvefixes()`

```
1 条 CVE 记录
    ├─ vulnerable_code →  {"id": "CVE-xxx-vuln",  "label": 1, "cwe": "CWE-835"}
    └─ fixed_code      →  {"id": "CVE-xxx-fixed", "label": 0, "cwe": ""}
```

**这是整个项目最核心的一次变换。** 两个要点：

1. **安全样本不是单独收集的**，是把"修复后的版本"当负样本。所以安全样本天然和漏洞样本
   高度相似（往往只差几行），模型必须学会分辨细微差异，而不是靠整体风格猜。
2. **两个版本共用同一个 `group_id`**：

   ```python
   group = f"cvefixes::{cve_id}::{hash}"     # scripts/build_dataset.py:260
   ```

   这是为了第 6 步的防泄漏划分 —— 这一对"双胞胎"必须同进同出。

字段映射全表：

| 原始列 | → 输出字段 | 变换 |
|---|---|---|
| `cve_id` | `id` | 拼 `-vuln` / `-fixed` 后缀 |
| `hash` + `cve_id` | `group_id` | `cvefixes::{cve_id}::{hash}` |
| `repo_url` | `project` | `rsplit("/", 1)[-1]`，即 URL 最后一段 |
| `cwe_id` | `cwe` | 经 `_norm_cwe` 规范化 |
| `cwe_name` | `cwe_name` | strip；修复版本置空 |
| `language` | `language` | strip |
| `vulnerable_code` | `code`（+ `label=1`） | 经 `_clean_code` 清洗 |
| `fixed_code` | `code`（+ `label=0`） | 经 `_clean_code` 清洗 |

## 3 · 清洗

| 函数 | 位置 | 做什么 | 为什么 |
|---|---|---|---|
| `_clean_code()` | `scripts/build_dataset.py:103` | `\r\n` / `\r` → `\n`，去掉首尾空白 | **不统一换行符，去重会失效** —— 同一段代码在 Windows 和 Linux 上算出的 MD5 不同 |
| `_norm_cwe()` | `scripts/build_dataset.py:126` | 剥掉 `CWE-`/`CWE` 前缀，只留数字，`int()` 去前导零 | 原始数据里 `CWE-79` / `79` / `cwe_79` / `NVD-CWE-noinfo` 混着写，不统一会把同一个 CWE 当成好几个类 |
| `_md5()` | `scripts/build_dataset.py:81` | `hashlib.md5(text.encode("utf-8", errors="ignore"))` | 用 MD5 而非内置 `hash()`，因为内置 hash 每次进程启动都不一样，无法跨运行去重 |

## 4 · 过滤、截断、去重

**函数**：`scripts/build_dataset.py:631` `main()`（第 660-687 行）

```python
for r in BUILDERS[source](raw_dir, cfg):     # :662  按数据源选构建器
    if len(code) < min_chars: continue       # :664  丢掉 < 30 字符的碎片
    r["code"] = truncate_code(code, 20000)   # :668  超过 20,000 字符做头尾截断
    raw_records.append(r)

if cfg["data"]["dedup"]:                     # :676
    h = _md5(r["code"])                      # :680  按代码内容 MD5 去重
    r["code_hash"] = h                       # :684  同时把哈希写进样本
```

| 步骤 | 阈值（默认） | 效果 |
|---|---|---|
| 长度过滤 | `< 30` 字符丢弃 | 去掉 `}`、`return;` 这种没有语义的碎片 |
| 长度截断 | `> 20,000` 字符 | 头 60% + 尾 40%，中间插占位注释（`src/utils.py:141` `truncate_code`） |
| 去重 | 按 code 的 MD5 | CVEfixes 里有些 CVE 的 `vulnerable_code` 和 `fixed_code` 完全相同，必须去掉 |

> `truncate_code` 在这里（20,000）和训练时（8,000）**被调用了两次**，阈值不同。
> 这里是"别让超长文件撑爆内存"，训练那次是"别让超长样本拖慢每个 batch"。

## 5 · 分任务：特征和标签在这里定下来

**函数**：`scripts/build_dataset.py:546` `prepare_task_data()`

这是**两个模型的标签分岔点**：

| | 检测模型 | 分类模型 |
|---|---|---|
| **特征** | `code` 文本 | `code` 文本（**同一个字段**） |
| **标签** | `0` = safe / `1` = vulnerable | `0 ~ 27` 的**类别下标** |
| 样本池 | 全部记录 | **只有** `label == 1` 且 `cwe` 非空的 |
| 类别数 | 2 | 28 |
| 代码 | `:598` `pool = list(records)` | `:595` `pool = [r for r in records if r["label"] == 1 and r["cwe"]]` |

分类的数字编号怎么来的（`:601-623`）：

```python
counter = Counter(r["cwe"] for r in pool)              # 统计每个 CWE 多少条
kept = [(c, n) for c, n in counter.most_common()       # 按样本量降序
        if n >= min_n][:top_k]                          # 只留前 27 个
cwe_to_id = {c: i for i, (c, _) in enumerate(kept)}     # CWE 字符串 → 0..26
other_id  = len(cwe_to_id)                              # OTHER = 27
r["label"] = cwe_to_id.get(r["cwe"], other_id)          # 长尾全部映射到 OTHER
```

所以 `0` 是最高频的 CWE-119、`1` 是 CWE-79……排不进前 27 的长尾全部归到 `OTHER`（编号 27）。
**最终类别数 = 保留的 CWE 数 + 1**，这个 `+1` 漏了会让 `CrossEntropyLoss` 报
"weight tensor should be defined either for all N classes"。

实测（`merged` 数据源）：

```json
{"task": "classification", "num_labels": 28,
 "id2name": {"0": "CWE-119", "1": "CWE-79", "2": "CWE-20", ... "27": "OTHER"}}
```

## 6 · 划分：为什么按 group 而不是按样本

**函数**：`scripts/build_dataset.py:459` `split_groups()`

```
❌ 错误做法：random.shuffle(records) 后切三段
✅ 正确做法：先按 group_id 聚簇，打乱【簇】的顺序，再切三段
```

代码（`:500-519`）：

```python
groups.setdefault(r["group_id"], []).append(r)   # :503  同一 CVE 聚到一起
random.Random(seed).shuffle(keys)                # :507  打乱的是【簇】，不是样本
buckets = {"train": keys[:n_train], "val": ..., "test": ...}
return {k: [r for g in v for r in groups[g]] for k, v in buckets.items()}  # :519 展开回去
```

**不这么做的后果**（`:484-492` 的注释举了例子）：

```python
{"code": "char buf[10]; strcpy(buf, user_input);",  "label": 1}   # 漏洞版本
{"code": "char buf[10]; strncpy(buf, user_input, 10);", "label": 0}  # 修复版本
```

两者只差一个函数名。随机划分会让一条进训练集、另一条进测试集 ——
模型在测试集上遇到的是**训练样本的近邻副本**，指标虚高到 0.99，换到真实新漏洞上一塌糊涂。

> ⚠️ 注意：这个机制只保证**同源内**同 CVE 不跨集。项目目前**没有**做跨源近重复审计，
> 也没有做跨项目（同一个 GitHub 仓库）的泄漏检查。`merged` 数据源尤其要注意这一点。

## 8 · 训练时：文本 → 张量

**函数**：`src/data.py:29` `VulnDataset`（`:69` `__getitem__`）、
`src/data.py:121` `DynamicPaddingCollator`

```python

code = truncate_code(rec["code"], self.max_code_chars)   # :92  头 60% + 尾 40%，插占位注释
enc = self.tokenizer(code, truncation=True,              # :98  CodeBERT 的 byte-level BPE
                     max_length=self.max_length,         #      超长截断到 512 token

```

```python

                           pad_to_multiple_of=8)         # :178 对齐到 8 的倍数（Tensor Core 要求）
```

**为什么要动态 padding**：代码长度差异极大（几十 ~ 上千 token）。固定补到 512 的话，
一个 40 / 120 / 800 的 batch 要算 1536 个位置，动态 padding 只要约 808 —— 实测训练快 2~3 倍。

一个真实例子（`demo_verified/test_01.c` 的 `pop3_regular_transfer`，871 字符）：

```text
'CURLcode pop3_regular_transfer(struct connectdata *conn,\r\n ...'
  → tokenize（403 token，没超 512）
  → [0, 347, 42703, 20414, 3495, 246, 1215, ...]
  → ['<s>', 'C', 'URL', 'code', 'Ġpop', '3', '_', 'regular', '_', 'transfer', ...]
```

> `<s>` 是 RoBERTa 系的起始符；`Ġ` 表示"前面有个空格"（byte-level BPE 的写法）。

## 9 · 模型

**函数**：`src/models.py:43` `VulnClassifier`（`:118` `forward`）、
`src/models.py:190` `build_tokenizer()`

```text
input_ids (B, L) + attention_mask (B, L)
    │  AutoModel.from_pretrained(model_name)            # models.py:77  加载预训练编码器
    ▼
CodeBERT 编码器（124M 参数，全参数微调，不冻结任何层）
    │  last_hidden_state (B, L, 768)
    ▼
池化：取 [CLS] 位置 → (B, 768)                          # models.py:175
    │  nn.Dropout(0.1)
    ▼
nn.Linear(768, K)                                       # models.py:94  随机初始化
    │
    ▼
logits (B, K)  →  nn.CrossEntropyLoss                   # models.py:186
```

| 参数 | 检测模型 | 分类模型 |
|---|---|---|
| `K`（`num_labels`） | 2 | 28 |
| 分类头参数量 | 768×2+2 ≈ 1.5K | 768×28+28 ≈ 21.5K |
| 占总参数比 | < 0.001% | 约 0.017% |

**池化用 `[CLS]` 而不是平均池化**：BERT 预训练时就用这个位置做句子级任务，它天然承载了整体语义
（`models.py:174` 的注释）。

注意 `forward` 里传的是**未归一化的 logits**，`CrossEntropyLoss` 内部会做 `log_softmax`
（`models.py:183-186` 的注释专门强调了不要提前 softmax）。

**分层学习率**（`src/models.py:235` `get_parameter_groups`）—— 三组参数：

| 组 | 内容 | 学习率 | 权重衰减 |
|---|---|---|---|
| 1 | 编码器里需要衰减的权重 | `2e-5` | `0.01` |
| 2 | 编码器的 bias / LayerNorm | `2e-5` | **0** |
| 3 | 分类头 | `1e-4`（5 倍） | `0.01` |

- 分类头学习率更大：它是**随机初始化的**，一开始输出全是噪声，需要更大步长才能收敛。
- bias / LayerNorm 不衰减：权重衰减会把参数往 0 拉，而这两类参数本来就该接近 1，
  强行拉会损害表达能力。这是 BERT 微调的通行做法。

其余：梯度裁剪 `max_grad_norm=1.0`、梯度累积、warmup 10%、早停 `patience=2`。

## 12 · 前端：文件 → HTTP 请求

**文件**：`web/src/api.ts`

| 函数 | 位置 | 做什么 |
|---|---|---|
| `readFileBytes()` | `:155` | `await file.arrayBuffer()` —— 拿**原始字节** |
| `toBase64()` | `:144` | 按 `0x8000` 分块转 base64 |
| `runScan()` | `:91` | POST `/api/scan` |

```ts
// web/src/api.ts:91
files: files.map(f => ({
  client_id: f.client_id,          // crypto.randomUUID() 生成，App.tsx:37
  name: f.name,
  content_b64: toBase64(f.bytes),  // 分块转换

```

两个刻意的设计：

- **读字节而不是读文本**（`api.ts:82-90` 的注释）：`src/extract.py` 是**以字节为真相源**解析的，
  能正确处理 GBK 等非 UTF-8 文件。中间做一次 UTF-8 往返会让字节偏移改变，
  `start_line` / `end_line` 全部错位。
- **分块 base64**：`String.fromCharCode(...arr)` 展开大数组会爆栈，所以 `0x8000` 一块。

`web/vite.config.ts` 把 `/api/*` 代理到 `http://127.0.0.1:8000`，所以前端代码里始终写相对路径。

落盘（`_run_scan`，`:349-359`）：

```python
tmp = Path(tempfile.mkdtemp(prefix="scanman_web_"))   # 临时目录
for i, up in enumerate(uploads):
    sub = tmp / f"{i:04d}"                            # 每个文件一个序号子目录
    (sub / up.name).write_bytes(up.data)              # 原样字节，不做任何编码转换
```

**为什么要序号子目录**：两个都叫 `t.c` 的文件平铺在一起会**静默互相覆盖**
（侧栏显示 2 行、报告里只有 1 条）。

**为什么锁要包住整个 handler**（`SCAN_LOCK`，`:120`）：`src/extract.py:284` 的 `_load_parser`
是 `lru_cache` 的**共享单例**，而 tree-sitter 的 `Parser` **不是线程安全的**。
抽取发生在 GPU 之外，若只锁推理那一段，两个并发请求会同时对同一个 `Parser` 调 `parse()`，
表现为 **access violation 直接杀进程** —— 没有 traceback、没有日志。

# 第三部分 · 训练与推理的落差

这是理解"为什么模型表现是这样"的关键。

| | 训练侧 | 推理侧 |
|---|---|---|
| 数据来源 | CVE 修复 diff 的**补丁块（hunk）** | tree-sitter 抽的**完整函数** |
| 首行像函数签名的比例 | `cvefixes` **22.7%** / `merged` 53.2% | **100%** |
| 平均长度 | 1,922 / 1,246 字符 | 1,036 字符 |
| 位置 | 常从函数中间截出 | 从 `{` 到 `}` |

实测抽样 5,000 条 `cvefixes_detection_train.jsonl`，只有 **22.7%** 的样本首行像函数签名
—— 也就是说近八成的训练样本是**函数中间的一段**。

**后果**（`docs/07` 第 6 节有完整实测）：模型对自己训练分布内的真实代码能给 78~92% 的
漏洞概率，但对**短小的、手写的教科书式 C 代码**，概率最高只到 54%、多数落在 10~36%，
连"不安全版 vs 安全版"的排序都常常是反的。

`scripts/spike_align.py` 就是专门量化这个落差的：它把训练侧结构、真实项目结构、
带标签实测三组 F1 摆在一起对比，结论写在 `outputs/spike_align.json`。

> **对演示的直接含义**：素材只能取自真实代码。"自己写几个有漏洞的小例子"是走不通的 ——
> `demo_verified/` 里的 30 个函数就是从真实 CVE 测试划分里挑出来的。
