# 全流程与接口规范

> **这份文档回答**：用户丢进来一个项目（或一个文件），到拿到"哪个函数有漏洞、是什么漏洞"的结果，
> 中间经过了哪些步骤、每一步的输入输出**类型是什么**、最终报告的**字段含义**是什么。

本文档是**接口契约**：字段名、类型、出现条件都以这里的定义为准。
`scan_project.py` 的报告结构改动必须先改这里。

---

## 第 0 节：需求定义

### 要解决的问题

给一个代码项目，找出**哪些函数有漏洞**，并判断**是哪一类漏洞（CWE）**。

### 两个任务

| 任务 | 类型 | 输入 | 输出 |
|---|---|---|---|
| **检测** | 二分类 | 一个函数 | 有漏洞 / 无漏洞 |
| **分类** | 多分类 | **有漏洞的**函数 | 属于哪个 CWE 类别 |

### 为什么是两个模型而不是一个

分类训练数据**全部来自漏洞样本**（`build_dataset.py` 只取 `label==1` 且有 `cwe` 的记录），
类别里**没有"安全"这一项**。

如果用一个模型同时做两件事，就必须喂它安全样本 —— 而安全样本没有对应类别，
等于逼模型在 27 个 CWE 里硬挑一个。**产出的噪声和真结果长得一模一样**，审查的人分不出来。

所以采用**两级级联**：先检测，命中的才送分类。

```
全部函数 ──▶ [检测模型] ──┬── safe      ──▶ 结束
                          └── vulnerable ──▶ [分类模型] ──▶ CWE 类别 + Top-5
```

## 第 1 节：全流程总览

```
┌─────────────┐
│ 用户输入     │  一个目录（项目）或单个源文件
└──────┬──────┘
       │
       ▼
┌──────────────────────────────────────────────────────────┐
│ ① 文件收集                        scan_project.scan_files │
│    遍历目录、按扩展名筛选、跳过 .git/node_modules、体积上限  │
│    出：list[FileResult] + list[SkippedItem]               │
└──────┬───────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────────┐
│ ② 函数抽取                        src.extract（tree-sitter）│
│    把每个源文件解析成语法树，切出其中的函数                  │
│    出：list[FunctionInfo]                                 │
└──────┬───────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────────┐
│ ③ 检测推理                        run_inference            │
│    每个函数送入检测模型，得到"有漏洞/无漏洞"                 │
│    出：dict[(文件序号, 函数序号), DetectionPred]           │
└──────┬───────────────────────────────────────────────────┘
       │
       │  只挑 verdict == "vulnerable" 的
       ▼
┌──────────────────────────────────────────────────────────┐
│ ④ 分类推理                        run_classification       │
│    命中的函数送入分类模型，得到 CWE 类别                     │
│    出：dict[(文件序号, 函数序号), ClassificationPred]      │
└──────┬───────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────────┐
│ ⑤ 组装报告                        build_report             │
│    合并上面所有产物，写成 JSON                              │
│    出：Report（可 JSON 序列化）                            │
└──────────────────────────────────────────────────────────┘
```

**步骤 ③④ 是可选的**：不给 `--checkpoint` 就只做 ①②（纯函数抽取统计）；
给了 `--checkpoint` 不给 `--classifier` 就只做检测。

## 第 2 节：每一步的类型定义

> 下述类型用 Python 的类型标注写。`|` 表示"或"，`X | None` 表示可能为空。

### 2.1 `FileResult` —— 一个文件的抽取结果

```python
FileResult = {
    "path":                str,          # 相对路径，POSIX 风格（用 / 不用 \）
    "language":            str | None,   # "c" / "cpp" / "python" / "php" / ...
    "parse_ok":            bool,         # 语法树有无 ERROR 节点
    "num_bytes":           int,          # 文件字节数
    "function_count":      int,          # 成功切出的函数个数
    "functions_discarded": int,          # 因语法错误被丢弃的函数个数
    "functions":           list[FunctionInfo],
}
```

**为什么路径用 POSIX 风格**：报告要能在 Windows 上生成、在 Linux CI 里比对，
绝对路径和反斜杠都不满足这个要求（见 `scan_project.py` 的 `build_report` docstring）。

### 2.2 `FunctionInfo` —— 一个函数

```python
FunctionInfo = {
    "name":        str,             # 函数名
    "start_line":  int,             # 起始行号，从 1 开始
    "end_line":    int,             # 结束行号
    "start_byte":  int,             # 起始字节偏移
    "end_byte":    int,             # 结束字节偏移
    "code":        str,             # 完整函数源码（含函数签名、装饰器）
    "node_type":   str,             # tree-sitter 节点类型，便于排查抽取问题
    "language":    str,             # 语言键
    "depth":       int,             # 嵌套深度：0=顶层，>0=嵌套函数
    "parent_name": str | None,      # 外层函数名；顶层函数为 None
}
```

> ⚠️ **行号是由字节偏移推导的，不是读 `Node.start_point.row`**。
> 在 tree-sitter 0.26.0 这一代读 `.row` 会**非确定性段错误**（同样输入每轮崩的位置都不同）。
> 详见 `requirements.txt` 的警告和 `tests/test_extract.py::test_no_point_api_usage` 回归守卫。

### 2.3 `DetectionPred` —— 检测结果

```python
DetectionPred = {
    "label":            0 | 1,          # 0=安全，1=有漏洞
    "verdict":          str,            # "safe" | "vulnerable"
    "confidence":       float,          # 被判类别的概率，0~1
    "prob_safe":        float,          # 安全的概率
    "prob_vulnerable":  float,          # 有漏洞的概率
}
```

**判定规则**：`prob_vulnerable >= threshold` 时判为 `vulnerable`。

阈值的确定顺序（`VulnPredictor.__init__`）：

```
① 默认 0.5
     ↓ 被覆盖
② <检查点>/threshold.json 里的值（如果存在）
     ↓ 被覆盖
③ 命令行 --threshold 显式指定的值（优先级最高）
```

> ⚠️ **`train.py` 从不写 `threshold.json`**。训练完必须跑
> `scripts/tune_threshold.py --write`，否则推理会静默用 0.5。
> 在不平衡数据上，0.5 几乎肯定不是最优阈值。

### 2.4 `ClassificationPred` —— 分类结果

```python
ClassificationPred = {
    "label":      int,          # 类别下标（对应 label_map.json 的 id2name）
    "cwe":        str,          # CWE 编号，如 "CWE-119"
    "confidence": float,        # 最高类别的概率
    "topk":       list[TopKItem],   # Top-5 候选
}

TopKItem = {
    "cwe":  str,        # CWE 编号
    "prob": float,      # 概率
}
```

> **只在检测命中时才存在**，且 `topk` 默认取 5 条。

### 2.5 `SkippedItem` —— 被跳过的文件

```python
SkippedItem = {
    "path":   str,      # 相对路径
    "reason": str,      # 跳过原因
}
```

常见原因：文件超过 `--max-file-size`、扩展名不支持、读取失败、解析异常。

## 第 3 节：最终报告 Schema

报告是**给人看也给程序读**的，顶层键名固定，**新增字段只加不改**。
`schema_version` 用于将来做破坏性变更时让消费方感知。

> **约定**：新增**可选**字段不递增 `schema_version`。当前版本 = `1`。

```jsonc
{
  "schema_version": 1,
  "tool": "scanman",
  "generated_at": "2026-09-21T13:08:09+08:00",   // 本地时区 ISO 8601
  "root": "C:/path/to/project",                  // 扫描根目录
  "checkpoint": "outputs/xxx/best",              // 检测模型；未启用推理时为 null
  "threshold": 0.215,                            // 实际生效的判定阈值；同上
  "classifier_checkpoint": "outputs/yyy/best",   // 分类模型；未启用分类时为 null

  "summary": {
    "files_scanned":        int,      // 扫描的文件数
    "files_skipped":        int,      // 跳过的文件数
    "functions_total":      int,      // 抽出的函数总数
    "functions_suspicious": int,      // ★ 判为有漏洞的函数数
    "functions_classified": int,      // 成功拿到 CWE 的函数数
    "languages": { "c": 1234, "cpp": 56 }   // 语言 → 函数数
  },

  "skipped": [ { "path": str, "reason": str } ],

  "files": [{
    "path":                str,
    "language":            str,
    "parse_ok":            bool,
    "num_bytes":           int,
    "function_count":      int,
    "suspicious_count":    int,       // ★ 这个文件里几个函数有漏洞
    "functions_discarded": int,
    "functions": [{
      // —— 第 2.2 节 FunctionInfo 的字段 ——
      "name": str, "start_line": int, "end_line": int,
      "start_byte": int, "end_byte": int,
      "node_type": str, "language": str,
      "depth": int, "parent_name": str | None,
      "code": str,                    // --no-code 时整个键不存在

      // —— 检测结果；不给 --checkpoint 时这三个键都不存在 ——
      "verdict":         "safe" | "vulnerable",
      "confidence":      float,
      "prob_vulnerable": float,

      // —— 分类结果；仅在 verdict=="vulnerable" 且跑了分类时存在 ——
      "cwe":      str,                // 如 "CWE-119"
      "cwe_topk": [ { "cwe": str, "prob": float } ]
    }]
  }]
}
```

### 字段出现条件（**容易踩坑，务必看清**）

| 字段 | 什么时候存在 |
|---|---|
| 整个 `verdict` / `confidence` / `prob_vulnerable` | 只有传了 `--checkpoint` |
| `cwe` / `cwe_topk` | 只有 `verdict == "vulnerable"` **且**传了 `--classifier` |
| `code` | 没传 `--no-code` 时存在 |

**为什么"没有就不写"而不是写 `null`**：`"verdict": null` 会被消费方误读成
"模型判定为安全"，`"cwe": null` 会被误读成"没有类别"。**不存在**和**判定为空**是两回事。

> 注意分类结果在报告里的键名是 **`cwe_topk`**，不是 `predict.py` 内部的 `topk` ——
> 换个更明确的名字，免得消费方以为它是通用的 top-k。

## 第 4 节：怎么用

### 4.1 只抽取函数（不加载模型，秒级）

```bash
python scripts/scan_project.py /path/to/project --output result.json --no-code
```

### 4.2 检测（找出哪些函数有漏洞）

```bash
python scripts/scan_project.py /path/to/project \
  --checkpoint outputs/<检测run>/best \
  --output result.json --no-code
```

### 4.3 检测 + 分类（完整级联）

```bash
python scripts/scan_project.py /path/to/project \
  --checkpoint  outputs/<检测run>/best \
  --classifier  outputs/<分类run>/best \
  --output result.json --no-code
```

### 4.4 常用参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `path` | 必填 | 要扫描的目录**或单个文件** |
| `--output` | `outputs/scan_result.json` | 报告输出路径 |
| `--checkpoint` | 无 | 检测模型目录；不给则只抽取 |
| `--classifier` | 无 | 分类模型目录；**必须与 `--checkpoint` 同时给** |
| `--device` | 自动 | `cpu` / `cuda` / `cuda:1` |
| `--batch-size` | 16 | 推理批大小 |
| `--threshold` | 读检查点 | 判定阈值，显式指定时优先级最高 |
| `--max-file-size` | 2000000 | 单文件字节上限，超过则跳过 |
| `--outer-only` | 关 | 只统计顶层函数，丢弃嵌套函数与闭包 |
| `--skip-dir` | 无 | 额外跳过的目录名，可重复 |
| `--no-skip` | 关 | 不跳过任何目录（默认跳过 `.git`/`node_modules`/`venv` 等） |
| `--no-code` | 关 | 报告里不包含函数源码，体积大幅缩小 |

## 第 5 节：用户案例

> **用户诉求**：我给一个 `.cpp` 文件，你要告诉我这个文件里有几个函数有漏洞、分别是什么漏洞。

### 输入

`demo/parser.c`：

```c
#include <string.h>
#include <stdlib.h>

int safe_copy(const char *src, char *dst, size_t n) {
    if (n == 0) return -1;
    snprintf(dst, n, "%s", src);
    return 0;
}

void parse_header(char *line) {
    char buf[64];
    strcpy(buf, line);          /* 栈缓冲区溢出 */
    printf("%s\n", buf);
}

char *make_greeting(const char *name) {
    char *out = malloc(256);
    strcpy(out, "hello ");
    strcat(out, name);
    return out;
}
```

### 命令

```bash
python scripts/scan_project.py demo/parser.c \
  --checkpoint  outputs/<检测run>/best \
  --classifier  outputs/<分类run>/best \
  --output demo/result.json
```

### 终端输出（`print_summary`）

```
========================================================================
扫描结果
========================================================================
  扫描根目录 : demo
  文件       : 1 个（跳过 0 个）
  函数       : 3 个
  检查点     : outputs/<检测run>/best
  判定阈值   : 0.2150
  可疑函数   : 2 个（占 66.7%）
  分类器     : outputs/<分类run>/best
  已分类     : 2 个（命中函数的 CWE 结果）
  语言分布   : c 3

  最可疑的 2 个函数：
    parser.c:10   parse_header  conf=0.912  CWE-120
    parser.c:16   make_greeting conf=0.634  CWE-120
========================================================================
```

## 第 6 节：能力边界（**汇报前必须知道**）

### 6.1 语言覆盖

`src/extract.py` 的**抽取器**支持 7 种语言：

| 语言 | 扩展名 | 抽取 |
|---|---|---|
| C | `.c` `.h` | ✅ |
| C++ | `.cpp` `.cc` `.hpp` | ✅ |
| Python | `.py` | ✅ |
| JavaScript | `.js` | ✅ |
| TypeScript | `.ts` | ✅ |
| TSX | `.tsx` | ✅ |
| PHP | `.php` | ✅ |

**但"能抽取"不等于"模型认得"。** 模型只在训练数据覆盖的语言上可靠。

### 6.2 训练数据的语言分布（实测）

| 数据集 | 训练量 | 语言 | 形态 |
|---|---:|---|---|
| `bigvul_detection` | 140,004 | C 98.6% / C++ 1.4% | ✅ 完整函数 |
| `diversevul_detection` | 404,552 | C/C++ | ✅ 完整函数 |
| `merged_detection` | 429,308 | 29 种，但 **97.6% 是 C/C++** | ✅ 主体是完整函数 |
| `cvefixes_detection` | 15,147 | 27 种 | ❌ diff 碎片 |

**结论**：**除 C/C++ 外，其它语言的可训练数据都只有几百到几千条**，训不出可靠能力。

### 6.3 核心矛盾（选数据集时的唯一判据）

```
要「多语言」  → 只能用 cvefixes → 它是 diff 碎片 → 扫真实项目误报高
要「函数级」  → 只能用 bigvul/diversevul/merged → 纯 C/C++ → 只有单语言
```

**没有"多语言 + 函数级"的现成数据。** 这个取舍必须在训练前定下来。

### 6.4 已知限制

| 限制 | 说明 |
|---|---|
| 单语言 | 当前数据条件下，模型只在 C/C++ 上可靠 |
| 标签噪声 | BigVul 的标签质量是文献公认的问题，会压制 precision 上限 |
| 类别长尾 | 分类任务里最小的类只有几十条样本 |
| 跨数据集泛化差 | 漏洞检测模型的跨数据集泛化是这个领域的公开难题 |

## 第 7 节：演示方案

> **原则**：指标第一，演示第二。演示的作用是"让结论看得见"，不是"重新证明一遍"。

### 7.1 三个兜底手段

**① 用阈值控制演示效果（最有效的杠杆）**

阈值调高 → 判为漏洞的变少但更准；调低 → 抓得多但误报多。
演示时用**高阈值**，保证标红的基本都是真漏洞。这是真实的权衡，不是造假。

**② 演示素材用"小而精"的 C 文件**

10~30 个文件的 C 项目，里面明确有 1~2 个经典漏洞（`strcpy` 栈溢出、格式化字符串等）。
命中数适中 —— 不是 0（显得没用），也不是满屏（显得瞎报）。

**③ 指标演示和扫描演示分开**

| 环节 | 材料 |
|---|---|
| 指标 | 测试集 F1 / AUC / PR-AUC，阈值扫描表 |
| 演示 | 现场扫一个小 C 项目，展示报告和 CWE 分类结果 |

### 7.2 演示前必须确认的三件事

1. **模型是真的**：`best/` 下有权重文件，`results.json` 有真实数字
2. **阈值调过了**：`best/threshold.json` 存在（`tune_threshold.py --write` 的产物）
3. **演示素材验证过**：提前跑一遍，确认输出结果符合预期
