# 全流程与接口规范

> **这份文档回答**：用户丢进来一个项目（或一个文件），到拿到"哪个函数有漏洞、是什么漏洞"的结果，
> 中间经过了哪些步骤、每一步的输入输出**类型是什么**、最终报告的**字段含义**是什么。

本文档是**接口契约**：字段名、类型、出现条件都以这里的定义为准。
`scan_project.py` 的报告结构改动必须先改这里。第 8 节同样约束 `scripts/serve.py`。

**目录**：0 需求 → 1 全流程 → 2 类型定义 → 3 报告 Schema → 4 怎么用（命令行）
→ 5 用户案例（实测可复现）→ 6 能力边界 → 7 演示方案 → **8 Web 接口**

---

## 第 0 节：需求定义

### 要解决的问题

给一个代码项目，找出**哪些函数有漏洞**，并判断**是哪一类漏洞（CWE）**。

### 两个任务

| 任务 | 类型 | 输入 | 输出 |
|---|---|---|---|
| **检测** | 二分类 | 一个函数 | 有漏洞 / 无漏洞 |
| **分类** | 多分类 | **有漏洞的**函数 | 属于哪个 CWE 类别 |

### 为什么是两个模型而不是一个

分类训练数据**全部来自漏洞样本**（`build_dataset.py` 只取 `label==1` 且有 `cwe` 的记录），
类别里**没有"安全"这一项**。

如果用一个模型同时做两件事，就必须喂它安全样本 —— 而安全样本没有对应类别，
等于逼模型在几十个 CWE 里硬挑一个。**产出的噪声和真结果长得一模一样**，审查的人分不出来。

所以采用**两级级联**：先检测，命中的才送分类。

```
全部函数 ──▶ [检测模型] ──┬── safe      ──▶ 结束
                          └── vulnerable ──▶ [分类模型] ──▶ CWE 类别 + Top-5
```

## 第 1 节：全流程总览

```
┌─────────────┐
│ 用户输入     │  一个目录（项目）或单个源文件
└──────┬──────┘
       │
       ▼
┌──────────────────────────────────────────────────────────┐
│ ① 文件收集               scan_project.iter_source_files │
│     遍历目录、按扩展名筛选、跳过 .git / node_modules     │
│     出：list[Path]                                       │
└──────┬───────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────────┐
│ ② 函数抽取                      scan_project.scan_files │
│     逐个文件解析语法树、切出函数（内部调 src.extract）   │
│     跳过二进制 / 体积超限 / 读失败                       │
│     出：list[FileResult]（含函数）+ list[SkippedItem]    │
└──────┬───────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────────┐
│ ③ 检测推理                        run_inference            │
│    每个函数送入检测模型，得到"有漏洞/无漏洞"                 │
│    出：dict[(文件序号, 函数序号), DetectionPred]           │
└──────┬───────────────────────────────────────────────────┘
       │
       │  只挑 verdict == "vulnerable" 的
       ▼
┌──────────────────────────────────────────────────────────┐
│ ④ 分类推理                        run_classification       │
│    命中的函数送入分类模型，得到 CWE 类别                     │
│    出：dict[(文件序号, 函数序号), ClassificationPred]      │
└──────┬───────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────────┐
│ ⑤ 组装报告                        build_report             │
│    合并上面所有产物，写成 JSON                              │
│    出：Report（可 JSON 序列化）                            │
└──────────────────────────────────────────────────────────┘
```

**步骤 ③④ 是可选的**：不给 `--checkpoint` 就只做 ①②（纯函数抽取统计）；
给了 `--checkpoint` 不给 `--classifier` 就只做检测。

## 第 2 节：每一步的类型定义

> 下述类型用 Python 的类型标注写。`|` 表示"或"，`X | None` 表示可能为空。

### 2.1 `FileResult` —— 一个文件的抽取结果

```python
FileResult = {
    "path":                str,          # 相对路径，POSIX 风格（用 / 不用 \）
    "language":            str | None,   # "c" / "cpp" / "python" / "php" / ...
    "parse_ok":            bool,         # 语法树有无 ERROR 节点
    "num_bytes":           int,          # 文件字节数
    "function_count":      int,          # 成功切出的函数个数
    "functions_discarded": int,          # 因语法错误被丢弃的函数个数
    "functions":           list[FunctionInfo],
}
```

**为什么路径用 POSIX 风格**：报告要能在 Windows 上生成、在 Linux CI 里比对，
绝对路径和反斜杠都不满足这个要求（见 `scan_project.py` 的 `build_report` docstring）。

### 2.2 `FunctionInfo` —— 一个函数

```python
FunctionInfo = {
    "name":        str,             # 函数名
    "start_line":  int,             # 起始行号，从 1 开始
    "end_line":    int,             # 结束行号
    "start_byte":  int,             # 起始字节偏移
    "end_byte":    int,             # 结束字节偏移
    "code":        str,             # 完整函数源码（含函数签名、装饰器）
    "node_type":   str,             # tree-sitter 节点类型，便于排查抽取问题
    "language":    str,             # 语言键
    "depth":       int,             # 嵌套深度：0=顶层，>0=嵌套函数
    "parent_name": str | None,      # 外层函数名；顶层函数为 None
}
```

> ⚠️ **行号是由字节偏移推导的，不是读 `Node.start_point.row`**。
> 在 tree-sitter 0.26.0 这一代读 `.row` 会**非确定性段错误**（同样输入每轮崩的位置都不同）。
> 详见 `requirements.txt` 的警告和 `tests/test_extract.py::test_no_point_api_usage` 回归守卫。

### 2.3 `DetectionPred` —— 检测结果

```python
DetectionPred = {
    "label":            0 | 1,          # 0=安全，1=有漏洞
    "verdict":          str,            # "safe" | "vulnerable"
    "confidence":       float,          # 被判类别的概率，0~1
    "prob_safe":        float,          # 安全的概率
    "prob_vulnerable":  float,          # 有漏洞的概率
    "threshold":        float,          # 本次判定实际生效的阈值
}
```

> ⚠️ `threshold` **只在推理器的返回值里有，不进报告**（报告顶层已有一个
> `threshold` 字段，见第 3 节）。报告 schema 刻意不带它，别照这里去找。

**判定规则**：`prob_vulnerable >= threshold` 时判为 `vulnerable`。

阈值的确定顺序（`VulnPredictor.__init__`）：

```
① 默认 0.5
     ↓ 被覆盖
② <检查点>/threshold.json 里的值（如果存在）
     ↓ 被覆盖
③ 命令行 --threshold 显式指定的值（优先级最高）
```

> ⚠️ **`train.py` 从不写 `threshold.json`**。训练完必须跑
> `scripts/tune_threshold.py --write`，否则推理会静默用 0.5。
> 在不平衡数据上，0.5 几乎肯定不是最优阈值。

### 2.4 `ClassificationPred` —— 分类结果

```python
ClassificationPred = {
    "label":      int,          # 类别下标（对应 label_map.json 的 id2name）
    "cwe":        str,          # CWE 编号，如 "CWE-119"
    "confidence": float,        # 最高类别的概率
    "topk":       list[TopKItem],   # Top-5 候选
}

TopKItem = {
    "cwe":  str,        # CWE 编号
    "prob": float,      # 概率
}
```

> **只在检测命中时才存在**，且 `topk` 默认取 5 条。

### 2.5 `SkippedItem` —— 被跳过的文件

```python
SkippedItem = {
    "path":   str,      # 相对路径
    "reason": str,      # 跳过原因
}
```

常见原因：文件超过 `--max-file-size`、扩展名不支持、读取失败、解析异常。

## 第 3 节：最终报告 Schema

报告是**给人看也给程序读**的，顶层键名固定，**新增字段只加不改**。
`schema_version` 用于将来做破坏性变更时让消费方感知。

> **约定**：新增**可选**字段不递增 `schema_version`。当前版本 = `1`。

```jsonc
{
  "schema_version": 1,
  "tool": "scanman",
  "generated_at": "2026-09-21T13:08:09+08:00",   // 本地时区 ISO 8601
  "root": "D:\\Dev\\Projects\\ScanMan",           // 扫描根目录（见下方说明）
  "checkpoint": "outputs/xxx/best",              // 检测模型；未启用推理时为 null
  "threshold": 0.67,                             // 实际生效的判定阈值；同上
                                                 // （演示检测模型 threshold.json = 0.67）
  "classifier_checkpoint": "outputs/yyy/best",   // 分类模型；未启用分类时为 null

  "summary": {
    "files_scanned":        int,      // 扫描的文件数
    "files_skipped":        int,      // 跳过的文件数
    "functions_total":      int,      // 抽出的函数总数
    "functions_suspicious": int,      // ★ 判为有漏洞的函数数
    "functions_classified": int,      // 成功拿到 CWE 的函数数
    "languages": { "c": 1234, "cpp": 56 }   // 语言 → 函数数
  },

  "skipped": [ { "path": str, "reason": str } ],

  "files": [{
    "path":                str,
    "language":            str,
    "parse_ok":            bool,
    "num_bytes":           int,
    "function_count":      int,
    "suspicious_count":    int,       // ★ 这个文件里几个函数有漏洞
    "functions_discarded": int,
    "functions": [{
      // —— 第 2.2 节 FunctionInfo 的字段 ——
      "name": str, "start_line": int, "end_line": int,
      "start_byte": int, "end_byte": int,
      "node_type": str, "language": str,
      "depth": int, "parent_name": str | None,
      "code": str,                    // --no-code 时整个键不存在

      // —— 检测结果；不给 --checkpoint 时这三个键都不存在 ——
      "verdict":         "safe" | "vulnerable",
      "confidence":      float,
      "prob_vulnerable": float,

      // —— 分类结果；仅在 verdict=="vulnerable" 且跑了分类时存在 ——
      "cwe":      str,                // 如 "CWE-119"
      "cwe_topk": [ { "cwe": str, "prob": float } ]
    }]
  }]
}
```

### 字段出现条件（**容易踩坑，务必看清**）

| 字段 | 什么时候存在 |
|---|---|
| 整个 `verdict` / `confidence` / `prob_vulnerable` | 只有传了 `--checkpoint` |
| `cwe` / `cwe_topk` | 只有 `verdict == "vulnerable"` **且**传了 `--classifier` |
| `code` | 没传 `--no-code` 时存在 |

**为什么"没有就不写"而不是写 `null`**：`"verdict": null` 会被消费方误读成
"模型判定为安全"，`"cwe": null` 会被误读成"没有类别"。**不存在**和**判定为空**是两回事。

> 注意分类结果在报告里的键名是 **`cwe_topk`**，不是 `predict.py` 内部的 `topk` ——
> 换个更明确的名字，免得消费方以为它是通用的 top-k。

> ⚠️ **`root` 是唯一不遵守「POSIX 风格」的字段。**
> 写的是 `str(root)`，Windows 下就是反斜杠（上面那条路径是实测值）。
> §2.1 的「POSIX 风格」只对文件项的 `path` 成立 —— 那个是 `p.relative_to(root).as_posix()`。
> 另外**网页版会覆写这个字段**（见第 7 节），消费方不要拿它当路径解析。

## 第 4 节：怎么用

### 4.1 只抽取函数（不加载模型，秒级）

```bash
python scripts/scan_project.py /path/to/project --output result.json --no-code
```

### 4.2 检测（找出哪些函数有漏洞）

```bash
python scripts/scan_project.py /path/to/project \
  --checkpoint outputs/<检测run>/best \
  --output result.json --no-code
```

### 4.3 检测 + 分类（完整级联）

```bash
python scripts/scan_project.py /path/to/project \
  --checkpoint  outputs/<检测run>/best \
  --classifier  outputs/<分类run>/best \
  --output result.json --no-code
```

### 4.4 常用参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `path` | 必填 | 要扫描的目录**或单个文件** |
| `--output` | `outputs/scan_result.json` | 报告输出路径 |
| `--checkpoint` | 无 | 检测模型目录；不给则只抽取 |
| `--classifier` | 无 | 分类模型目录；**必须与 `--checkpoint` 同时给** |
| `--device` | 自动 | `cpu` / `cuda` / `cuda:1` |
| `--batch-size` | 16 | 推理批大小 |
| `--threshold` | 读检查点 | 判定阈值，显式指定时优先级最高 |
| `--max-file-size` | 2000000 | 单文件字节上限，超过则跳过 |
| `--outer-only` | 关 | 只统计顶层函数，丢弃嵌套函数与闭包 |
| `--skip-dir` | 无 | 额外跳过的目录名，可重复 |
| `--no-skip` | 关 | 不跳过任何目录（默认跳过 `.git`/`node_modules`/`venv` 等） |
| `--no-code` | 关 | 报告里不包含函数源码，体积大幅缩小 |

## 第 5 节：用户案例

> **用户诉求**：我给一个 C 文件，你要告诉我这个文件里有几个函数有漏洞、分别是什么漏洞。

> ✅ **本节的输入、命令和输出都是实测的，可以直接照抄复现。**
> 用的是随仓库发布的测试夹具 `demo_verified/test_05.c`（5 个函数，3 命中 2 安全），
> 检查点就是 README「模型与已有实验」一节列出的那两个。

### 输入

`demo_verified/test_05.c`（节选，完整内容见文件）：

```c
static u32 nested_vmx_load_msr(struct kvm_vcpu *vcpu, u64 gpa, u32 count)
{
    /* 边界正确、错误路径完整的对照函数 —— 模型判为安全 */
    ...
}

static int userns_install(struct nsset *nsset, struct ns_common *ns)
{
    /* 权限相关，模型判为 CWE-264 */
    ...
}
```

### 命令

```bash
python scripts/scan_project.py demo_verified/test_05.c \
  --checkpoint  outputs/merged_detection_codebert/best \
  --classifier  outputs/merged_top27_codebert_e20/best \
  --output outputs/scan_test05.json
```

### 终端输出（`print_summary`）

```
========================================================================
扫描结果
========================================================================
  扫描根目录 : ...\ScanMan\demo_verified
  文件       : 1 个（跳过 0 个）
  函数       : 5 个
  检查点     : outputs/merged_detection_codebert/best
  判定阈值   : 0.6700
  可疑函数   : 3 个（占 60.0%）
  分类器     : outputs/merged_top27_codebert_e20/best
  已分类     : 3 个（命中函数的 CWE 结果）
  语言分布   : c 5

  最可疑的 3 个函数：
    test_05.c:76     keyring_search                   conf=0.909  CWE-476
    test_05.c:47     userns_install                   conf=0.867  CWE-264
    test_05.c:108    common_timer_get                 conf=0.788  CWE-125
========================================================================
```

> 注意这里的 `conf=` 用的是 `prob_vulnerable`（原样 3 位小数）。
> 另外两个**没**进榜的函数是 `nested_vmx_load_msr`（0.408）和 `__dentry_kill`（0.481）——
> 它们都低于 0.67，所以判为安全。

### JSON 报告（节选）

```jsonc
{
  "summary": {
    "files_scanned": 1, "files_skipped": 0,
    "functions_total": 5,
    "functions_suspicious": 3,        // ← 用户要的答案
    "functions_classified": 3,
    "languages": { "c": 5 }
  },
  "files": [{
    "path": "test_05.c", "language": "c", "parse_ok": true,
    "function_count": 5,
    "suspicious_count": 3,            // ← 这个文件里 3 个函数有漏洞
    "functions": [
      { "name": "nested_vmx_load_msr", "start_line": 11, "end_line": 44,
        "verdict": "safe", "confidence": 0.5921, "prob_vulnerable": 0.4079 },

      { "name": "userns_install", "start_line": 47, "end_line": 73,
        "verdict": "vulnerable", "confidence": 0.8674, "prob_vulnerable": 0.8674,
        "cwe": "CWE-264",
        "cwe_topk": [ {"cwe":"CWE-264","prob":0.9296},
                      {"cwe":"CWE-399","prob":0.0495} ] },

      { "name": "keyring_search", "start_line": 76, "end_line": 105,
        "verdict": "vulnerable", "confidence": 0.9093, "prob_vulnerable": 0.9093,
        "cwe": "CWE-476",
        "cwe_topk": [ {"cwe":"CWE-476","prob":0.7726},

```

> 判为 `vulnerable` 时它**恒等于** `prob_vulnerable`；判为 `safe` 时它是 **`p(安全)`**。
> 所以上面 `nested_vmx_load_msr` 的 `confidence` 是 0.5921（= 1 − 0.4079），不是 0.4079。
> **排序和展示一律用 `prob_vulnerable`**，语义才一致。

## 第 6 节：能力边界（**汇报前必须知道**）

### 6.1 语言覆盖

`src/extract.py` 的**抽取器**支持以下扩展名（`.h` 按 C 解析）：

| 语言 | 扩展名 | 抽取 |
|---|---|---|
| C | `.c` `.h` | ✅ |
| C++ | `.cc` `.cpp` `.cxx` `.hpp` `.hh` `.hxx` | ✅ |
| Python | `.py` `.pyw` `.pyi` | ✅ |
| JavaScript / JSX | `.js` `.mjs` `.cjs` `.jsx` | ✅ |
| TypeScript / TSX | `.ts` `.tsx` | ✅ |
| PHP | `.php` `.php3` `.php5` `.phtml` | ✅ |

**但"能抽取"不等于"模型认得"。** 模型只在训练数据覆盖的语言上可靠。

### 6.2 训练数据的语言分布（实测）

| 数据集 | 训练量 | 语言 | 形态 |
|---|---:|---|---|
| `bigvul_detection` | 140,004 | C 98.6% / C++ 1.4% | ✅ 完整函数 |
| `diversevul_detection` | 404,552 | C/C++ | ✅ 完整函数 |
| `merged_detection` | 429,308 | 29 种，但 **97.6% 是 C/C++** | ✅ 主体是完整函数 |
| `cvefixes_detection` | 15,147 | 27 种 | ❌ diff 碎片 |

**结论**：**除 C/C++ 外，其它语言的可训练数据都只有几百到几千条**，训不出可靠能力。

### 6.3 核心矛盾（选数据集时的唯一判据）

```
要「多语言」  → 只能用 cvefixes → 它是 diff 碎片 → 扫真实项目误报高
要「函数级」  → 只能用 bigvul/diversevul/merged → 纯 C/C++ → 只有单语言
```

**没有"多语言 + 函数级"的现成数据。** 这个取舍必须在训练前定下来。

### 6.4 已知限制

| 限制 | 说明 |
|---|---|
| 单语言 | 当前数据条件下，模型只在 C/C++ 上可靠 |
| 标签噪声 | BigVul 的标签质量是文献公认的问题，会压制 precision 上限 |
| 类别长尾 | 分类任务里最小的类只有几十条样本 |
| 跨数据集泛化差 | 漏洞检测模型的跨数据集泛化是这个领域的公开难题 |

## 第 7 节：演示方案

> **原则**：指标第一，演示第二。演示的作用是"让结论看得见"，不是"重新证明一遍"。

### 7.1 三个兜底手段

**① 用阈值控制演示效果（最有效的杠杆）**

阈值调高 → 判为漏洞的变少但更准；调低 → 抓得多但误报多。
演示时用**高阈值**，保证标红的基本都是真漏洞。这是真实的权衡，不是造假。

**② 演示素材用 `demo_verified/`，不要自己现写**

❗ **不要临时手写"经典漏洞"去演示。** 实测过四批自造探针（教科书式短函数、真实体量、
内核/OpenSSL 风格、残缺风格）共 31 个函数 —— 概率**最高只到 54%，多数落在 10~36%**，
全部低于 0.67 阈值。连"不安全版 vs 安全版"的排序都常常是反的。
这个检测器微调自四源合并的真实 CVE 修复提交，**短片段不在它的训练分布内**。

直接扫随仓库发布的夹具：

```bash
python scripts/scan_project.py demo_verified/ \
  --checkpoint outputs/merged_detection_codebert/best \
  --classifier outputs/merged_top27_codebert_e20/best \
  --output web/public/sample_report.json
```

13 个文件 / 30 个函数，其中 23 个命中、覆盖 12 种 CWE —— 命中数适中，
不是 0（显得没用），也不是满屏（显得瞎报）。每个函数都保证当前检查点判得对，
演示前用 `python scripts/check_fixture.py` 复查一遍即可。

**③ 指标演示和扫描演示分开**

| 环节 | 材料 |
|---|---|
| 指标 | 测试集 F1 / AUC / PR-AUC，阈值扫描表 |
| 演示 | 现场扫一个小 C 项目，展示报告和 CWE 分类结果 |

### 7.2 演示前必须确认的三件事

1. **模型是真的**：`best/` 下有权重文件，`results.json` 有真实数字。
   当前 `outputs/` 下 13 个检查点里 **7 个带权重**（演示用的
   `merged_detection_codebert` 与 `merged_top27_codebert_e20` 都在其中）；
   另 6 个只剩配置和标签映射，**不能拿来推理**。
2. **阈值调过了**：`best/threshold.json` 存在（`tune_threshold.py --write` 的产物），
   演示检测模型实测是 0.67。
3. **演示素材验证过**：跑 `python scripts/check_fixture.py`，
   它会逐条比对 `demo_verified/TRUTH.json`，确认 30 个函数全部判对。

## 第 8 节：Web 接口

> 命令行版（第 4 节）和网页版走的是**同一条管线**：`scripts/serve.py` 只是把
> HTTP 请求翻译成对 `scan_files` / `run_inference` / `run_classification` /
> `build_report` 的调用，**没有重写任何扫描逻辑**。同一份输入，两边结果逐条一致。

### 8.1 怎么起

```bash
# 终端 1 —— 后端（用装了 torch 的那个环境）
python scripts/serve.py                      # 监听 127.0.0.1:8000
# 终端 2 —— 前端
cd web && npm run dev                        # http://localhost:5173
```

`web/vite.config.ts` 已把 `/api` 代理到 `127.0.0.1:8000`，所以前端一律写相对路径。

启动参数：`--detector` / `--classifier`（默认就是演示用的两个 `outputs/*/best`）、
`--device`、`--port`（默认 8000，**改端口要同步改 Vite 的 proxy**）、`--batch-size`。

### 8.2 两个接口

```
GET  /api/health
  → { status, models_loaded, device, gpu, detector, classifier,
      threshold, num_labels, error }

POST /api/scan
  body: { files: [ { client_id, name, content_b64 } ] }
  → 200 { report: <本文件第 3 节的报告>, uploads: [ { client_id, name, path, status, reason? } ] }
```

`status` 的语义是给前端决定「开始检测」能不能点：
只有 **`ready`** 才代表"点了就快" —— 权重加载完之后还要预热 tree-sitter 语法包
和第一次 CUDA 前向，全都完成了才翻 `ready`。

### 8.3 上传侧约束（**与命令行版不同，这里会直接拒绝**）

| 约束 | 值 | 说明 |
|---|---|---|
| 单次文件数 | ≤ 32 | |
| 单文件大小 | ≤ `MAX_FILE_BYTES`（2,000,000 字节） | |
| 文件名 | `[A-Za-z0-9._-]{1,120}` | 挡路径穿越；Windows 保留名（`NUL`/`CON`…）另拦 |
| 扩展名 | 必须在 `LANGUAGE_BY_EXT` 里 | 21 种，见 §6.1 |
| 请求体 | ≤ 64 MiB | 超了返回 **413** |

⚠️ **参数不合法的文件返回 400，不会记进报告的 `skipped`。**
这是刻意的：前端要能区分「你传错文件了」（用户的错，改一下就好）
和「这个文件解析不了」（扫描器的结论，是报告的一部分）。
二进制、语法错、读失败这类仍然走 `skipped`，返回 200。

### 8.4 与命令行版的三处差异

1. **`root` 被覆写**成「本次上传的 N 个文件」—— 临时目录路径对看报告的人没意义。
   这是改**响应里的副本**，不是改 `build_report()`（它是带 `schema_version` 的 CI 契约）。
2. **同步返回**，没有任务编号和轮询接口。模型已常驻内存，单文件是秒级。
3. **并发**：同一时刻只接受一个扫描任务，第二个请求拿到 **409** 而不是排队
   （排队更糟：用户可能已经关掉页面，排队的扫描还是会照样烧 GPU）。
   模型没就绪时返回 **503**。

### 8.5 为什么上传的是"内容"而不是"路径"

浏览器出于安全**拿不到本地文件的绝对路径**（`<input type=file>` 只给文件名），
所以前端读**原始字节**、base64 编码后 POST 上来，服务端原样落盘。

> ⚠️ **必须传字节，不能用 `FileReader.readAsText()`。** `src/extract.py` 是
> **以字节为真相源**解析的（这样才处理得了 GBK 等非 UTF-8 文件）。
> 中间做一次 UTF-8 往返会让字节偏移改变，于是 `start_line` / `end_line` 全错，
> 界面上的源码行号会指向错误的位置。

服务只绑 `127.0.0.1`，不对外网开放。
