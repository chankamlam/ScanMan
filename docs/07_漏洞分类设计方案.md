## 二、现状盘点

### 2.1 数据侧：分类数据是齐的

| 文件 | 样本 | 原始 CWE 类别 | 单样本类 |
|------|-----:|-----:|-----:|
| `cvefixes_classification_train.jsonl` | 5,832 | **215** | 62 |
| `cvefixes_classification_test.jsonl` | 730 | **118** | 46 |

**注意"215"这个数**：本节说的"41 类"是**设计阶段的方案口径**，合并长尾之后的方案值；
不是原始类别数。合并规则在 `scripts/build_dataset.py`：

```
类别数 >= min_class_samples(30) 的类别才有资格保留
  → 恰好 40 类达标
再取 top_k_classes(40) 的前 40 名
  → 40 类，保留样本 4,738（81.2%）
剩下 18.8% 的样本归入 OTHER
  → 最终 40 + 1(OTHER) = 41 类
```

合并后的分布（train）：

| 指标 | 值 |
|------|----|
| 合并后类别数 | 41（40 CWE + OTHER） |
| OTHER 占比 | **18.8%**（1,094 / 5,832） |
| 最大 / 最小（保留类内） | CWE-79 = 1,103 / CWE-401 = 32 |
| 长尾比 | **34 : 1** |
| 前三类占比 | CWE-79 18.9%、CWE-125 4.9%、CWE-89 4.3%（合计 28.1%） |

> 长尾比 34:1 是**合并后**的比例（CWE-79 : CWE-401）。
> 不合并的原始 215 类长尾比会更极端，那正是要合并的理由。

`outputs/` 下保留了多组分类运行（`results.json` 与 `config.yaml` 进 Git，权重被 `.gitignore` 排除）：

| `merged_top27_codebert_e12` | 28 | 0.2302 | 0.7278 |
| `merged_top27_codebert_e8` | 28 | 0.2085 | 0.6841 |

**注意**：Git 仓库只保留 `label_map.json` / tokenizer 配置 / `config.yaml` / `results.json`，

### 2.3 推理侧：接口已经预留好了

`scripts/predict.py` 对分类任务**已经支持 Top-5 输出**（[`predict.py:239-251`](../scripts/predict.py#L239)），
不需要额外开发：

```python
{"label": 2, "cwe": "CWE-89", "confidence": 0.612,
 "topk": [{"cwe": "CWE-89", "prob": 0.612}, ...]}   # topk 长度 = min(5, 类别数)
```

`VulnPredictor` 会从 `label_map.json` 读到 `task: classification` 与对应的 `num_labels`
（CVEfixes 为 41，演示的 `merged_top27` 为 28），自动建出正确的分类头。
**这一层是通的，缺的只是权重。**

## 三、方案：两级级联

### 3.1 流程

```
项目文件
   │  src/extract.py（已实现）
   ▼
函数列表 ──→ ① 检测模型 ──→ 命中函数（verdict=vulnerable）
                            │
                            ▼
                       ② 分类模型 ──→ CWE-79 等（+ Top-5 候选）
                            │
                            ▼
                     按文件聚合的报告
```

### 3.2 为什么只对"命中函数"跑分类

| 理由 | 说明 |
|------|------|
| **数据天然衔接** | 分类训练数据全部来自漏洞样本（CVE 的 `vulnerable_code`），**没有"安全"这一类**。拿安全函数去分类，等于逼模型在 41 个 CWE 里硬挑一个 —— 结果必然是噪声 |
| **省算力** | 扫描一个 10 万函数的仓库，命中率通常远小于 1，逐函数跑两个模型纯属浪费 |
| **语义正确** | 分类回答的是"**这个漏洞**是哪一类"，前提是"这里确实有漏洞"。前提不成立时，答案本身没有意义 |

### 3.3 级联的损耗账（必须提前认清）

级联的最终效果**不可能超过上游检测**。用 CVEfixes 检测模型
`outputs/cvefixes_detection_6ep` 在测试集上的实测数字算一遍
（阈值 0.11，该 run 的 `best/threshold.json` 推荐值）：

| 环节 | 实测 | 对级联的后果 |
|------|------|------|
| 检测召回率 | 0.9402 | 5.98% 的真漏洞**根本进不了分类器**，级联召回率上限就被压在这 |
| 检测精确率 | **0.6232** | 送进分类器的样本里，**37.7% 其实是安全的** |
| 命中率 | 67.7%（1,287/1,902） | 分类算力开销 ≈ 函数总数 × 命中率 |

**精确率是级联的关键瓶颈**：0.6232 意味着分类器有三分之一以上的时间在做无用功，
而且这三分之一的输出**看起来和真结果一模一样**（一样是"CWE-79，置信度 0.71"），
人类审查时无法区分。这是级联方案最大的工程风险，不是模型精度问题。

### 3.4 报告接口的预留

`scripts/scan_project.py` 的 JSON schema 目前对每个函数输出
`verdict / confidence / prob_vulnerable`。加分类后建议**只增不改**：

```jsonc
{
  "verdict": "vulnerable",
  "confidence": 0.87,
  "prob_vulnerable": 0.87,
  "cwe": "CWE-89",                                            // 新增
  "cwe_topk": [{"cwe": "CWE-89", "prob": 0.61}, ...]           // 新增
}
```

新增可选字段**不递增** `schema_version`；只有当已有字段的含义或类型改变时才递增
（该字段的注释里已经写明这条约定）。

## 四、第一件事：正式训练一次

### 4.1 为什么这是第一步

分类训练已经完成：`scripts/train.py` 的分类分支、`weighted_loss`、Top-5 评估都可用，
演示模型 `merged_top27_codebert_e20` 的测试集指标为 Accuracy 0.3333 / Macro-F1 0.2392 /
Top-3 0.6041 / Top-5 0.7438（见 2.2）。下面保留当时"先训练拿到真实数字再谈集成"的推理过程。

### 4.2 预期：macro-F1 会很难看，这是正常的

数据本身决定了这一点，不是模型的问题：

| 原因 | 数据 |
|------|------|
| 长尾 | train 34:1（CWE-79 1,103 : CWE-401 32）；**test 更极端 —— 128:1** |
| 测试集有 46 个类只有 1 个样本 | macro-F1 里这些类各占 1/118 权重，且几乎不可能预测对 |
| OTHER 占 18.8% | 五分之一的样本没有具体类别可学，只能学到"这堆东西互不相似" |

**所以不要用 macro-F1 当验收指标。** 按 `01` 文档里检测模型的教训：
先把链路跑通、拿到真实数字，再决定优化方向。

### 4.3 该用什么指标

| 指标 | 建议 | 理由 |
|------|------|------|
| **Top-5 accuracy** | ✅ **主指标** | `predict.py` 已输出 Top-5。安全场景下"正确答案在前 5 里"对人有实用价值：审查者看 5 个候选，比看一个错的好 |
| **置信度门槛 + 弃答** | ✅ 推荐 | 置信度低于门槛时输出"有漏洞，类别不确定"，而不是硬猜。这比一个 30% 置信度的 CWE-79 有用得多 |
| macro-F1 | ⚠️ 仅作参考 | 会被 46 个单样本类严重拉低，跨模型比较时才用 |
| **Top-1 accuracy** | ⚠️ 仅作参考 | 41 类随机基线 2.4%（当前 28 类则是 1/28 ≈ 3.6%），只要显著高于它就算学到东西 |

### 4.4 类别体系：要不要重新设计

当前 41 类的划分是**数据驱动**的（谁样本多谁进），不是**语义驱动**的。
落地时会遇到一个实际问题：开发者看到 "CWE-787 越界写" 和 "CWE-125 越界读"
分成了两类，而这两者的修复动作往往一样。

三种选择：

| 方案 | 说明 | 当时判断 | **实际落地** |
|------|------|------|------|
| 保持 41 类 | 不动，先跑通 | ✅ 当时推荐 | ❌ 未采用 |
| 按 CWE 顶层类别归并 | 归成 10~15 类 | 若 Top-5 仍不好用 | ❌ 未采用 |
| **只保留 Top-N 高频类** | 其余全 OTHER | 若只关心常见的几类 | ✅ **已采用，取 N = 27** |

> ⚠️ **本节停留在"建议"阶段，实际做法和它不同。**
> 最终落地的是第三种：`scripts/relabel_classes.py --source merged --top-k 27`
> 产出 **Top-27 + OTHER = 28 类**（`--top-k` 默认就是 27），
> 命名为 `merged_top27_*`，对应的模型是 `outputs/merged_top27_codebert_e20`。
>
> 所以本文上面几节反复出现的「41 类」是**设计阶段的方案口径**，
> 当前生效的类别数以 `data/processed/merged_top27_classification_label_map.json`
> 的 `num_labels`（= 28）为准。41 类的那份数据与模型（`cvefixes_classification_*`）
> 仍在仓库里，作为**对照口径**保留。

## 五、曾经必修的 bug（已修复）

### `scripts/predict.py` —— 字符串标签崩溃（已修）

早期批量推理里对 gold 标签一律 `int(r["label"])`。分类任务的预测 `label` 是**类别下标**，
而人工用例（`docs/test_cases/classification_test_cases.jsonl`）里放的是 **CWE 名字**
（如 `"CWE-120"`），`int("CWE-120")` → `ValueError`，整个批量推理崩溃。

**现状**：`predict.py` 已抽出 `is_correct(pred, gold, task)`，按任务类型与 gold 形态分别处理：

```python
# 检测任务比 int；分类任务遇到 "CWE-120" 这类名字时比预测出的 cwe 字段；
# 两边都对不上就返回 None（跳过，不计入准确率）
```

对应测试见 `tests/test_predict_metrics.py`（数字字符串按下标比、分类比 CWE 名字、
大小写/空格不敏感、比不了返回 `None`）。

## 六、战略根治：训练数据与真实输入不是同一个分布

### 6.1 为什么必须正视这件事

`build_dataset.py` 喂给模型的**不是函数**，而是 CVE 修复提交里的 **diff 碎片**：

```
vulnerable_code = 该次修复中被删除的那些行的拼接
```

而扫描真实项目时，`src/extract.py` 抽出来的是**完整函数**（含签名、含缩进、
从 `def`/`int f(...)` 一直到闭合花括号）。两者不是同一个分布 ——
这是"检测模型能不能直接用于项目扫描"这个问题的核心，本次用 `scripts/spike_align.py`
把它**量出来**。

### 6.2 结构对比（`outputs/spike_align.json` 实测）

| 指标 | 训练碎片（train 15,147 条） | 真实项目函数（`src/` 47 个） | 差异 |
|------|------:|------:|------|
| 长度中位数 | **384** 字符 | **591** 字符 | **1.54 倍** |
| 完全无函数签名 | **89.6%** | **0.0%** | 质变 |
| 以签名开头 | **5.1%** | **95.7%** | 质变 |
| 短于 100 字符 | 18.5% | 0.0% | — |
| 长度 p90 / p99 | 4,407 / 20,025 | 1,542 / 2,670 | 碎片尾部极长 |

**读法**：训练数据里将近九成的样本**根本没有函数签名**（就是 diff 里被删掉的几行
语句，比如 `if (!verify(x)) {`），而真实项目抽出来的函数**几乎全部**以签名开头。
这不是"稍微有点不一样"，是**两种不同的东西**。

> 长度中位数 384 字符与 `01` 文档里记录的值**完全一致**，说明本 spike 的统计口径正确。
> （"含签名"比例的绝对值与早期记录不同：本脚本用正则粗判且**排除了控制语句开头**，
> 口径更严格 —— `if (...) {` 这类碎片在 diff 里最常见，不该算"有签名"。）

### 6.3 三组 F1 实测（阈值 0.11，`outputs/cvefixes_detection_6ep/best`）

| 组 | 数据 | n | F1 | 精确率 | 召回率 |
|----|---|--:|---:|---:|---:|
| **A** | 测试集全体（训练同分布的碎片） | 1,902 | 0.7495 | 0.6232 | 0.9402 |
| **B** | A 中"含函数签名"的子集 | 213 | 0.7500 | 0.6290 | 0.9286 |
| **C** | 人工手写的完整函数（真实扫描形态） | 20 | **0.6667** | 0.6154 | 0.7273 |

组 C 的混淆矩阵：`tn=4, fp=5, fn=3, tp=8`。

### 6.4 判定：**未触发**预设的实质性门槛

Spike 的判定规则是**事先写死在代码里**的（避免事后挑标准）：

```
C 的 F1 比 A 低超过 15 个点，或 C 的 recall < 0.5  →  判定漂移实质性存在
```

实测结果：

| 判据 | 实测 | 门槛 | 触发 |
|------|------|------|:---:|
| F1 落差（A → C） | **0.0829** | > 0.15 | ✗ |
| C 的召回率 | **0.7273** | < 0.5 | ✗ |

→ `distribution_shift_is_material: false`

**组 B 的结果也值得记一笔**：B（213 条含签名的碎片）的 F1 0.7500 与 A 的 0.7495
**几乎没有差别**。这说明"碎片里恰好包含一个函数签名"并不会让它更好或更坏 ——
签名存在与否**不是**决定因素，真正不同的是整体形态（长度、结构完整性）。

### 6.5 反过来看：为什么这个"通过"不能当成绿灯

**必须说清楚这里的张力**：组 C 没测出显著漂移，但用**同一个检查点、同一个阈值**
扫描本仓库自己的 `src/`（47 个怎么读都不可能算漏洞的 Python 函数），
结果是这样的（`outputs/scan_src_inference.json`）：

| 项 | 值 |
|----|----|
| 扫描范围 | `src/` 7 个文件、47 个函数 |
| 判定为可疑 | **15 个（31.9%）** |
| 最"可疑"的 5 个 | `_name_of` 0.873、`_collect_error_ranges` 0.867、`supported_extensions` 0.825、`__len__` 0.738、`to_dict` 0.690 |

这些函数是取名字、列扩展名、求字典长度 —— **零副作用的纯函数，不可能有漏洞**。

**两者为什么不矛盾**：

| | 组 C（20 条） | 真实仓库（47 个） |
|---|---|---|
| 来源 | 人工**精心编写**，每条都为模型"看得懂"而设计 | 随手抽出的真实代码，什么形态都有 |
| 结论的意义 | "完整函数**这个形态**本身不是障碍" | "真实项目上的**误报率**无法接受" |

组 C 的 F1 0.6667 里，精确率 0.6154 意味着**模型的告警有 38% 是错的**。
在 20 条上这个数字的噪声约 ±10 个点，但方向与 47 个函数上的 31.9% 一致。

> ⚠️ **所以第六节的正确结论是**：现有检查点用于真实项目扫描，
> **误报率不可接受**。组 C 的"通过"只说明完整函数形态可用，
> 不说明这个模型可以直接上生产。

### 6.6 根治路径：用本地函数级数据重训

`data/processed/` 里已经有**真正的函数级**原始数据（带可回溯字段）：

| 数据集 | 规模 | 特点 |
|--------|-----:|------|
| BigVul | ~15 万 | 函数级，带 CVE/CWE/项目/提交 |
| CodeXGLUE | ~2.1 万 | 函数级，二元标签，质量干净 |
| DiverseVul | ~50 万 | 函数级，规模最大，噪声也最多 |

**重训思路**：用这些函数级数据重训检测模型，让"训练分布 = 推理分布"
（都是完整函数），从根上消掉 6.2 表里那些质变差异。
本次 spike 的数据可以直接用作**重训前后的对照基线**。

> 这属于**战略级**改动（要重跑训练、重新评估、可能重调阈值），
> 不在本期范围，但方向应当明确 —— 继续在 diff 碎片上做增量优化的收益
> 会越来越小，因为输入分布本身就不对。

## 七、风险清单

| # | 风险 | 严重度 | 说明与对策 |
|--:|------|:---:|------|
| 1 | **检测误报链式放大** | 🔴 高 | 检测精确率 0.6232 → 分类器三分之一以上输入是噪声。**对策**：先提升检测精确率（或对分类结果做二次确认），再谈分类集成 |
| 2 | **置信度未校准** | 🟠 中 | 模型输出的 0.87 不等于"87% 把握"（未经校准）。**对策**：用验证集做温度缩放/等距回归，或者干脆只用 Top-5 + 人工审查 |
| 3 | **长尾类别学不动** | 🟠 中 | 34:1 长尾 + 46 个单样本测试类。`weighted_loss` 已默认开启，但可能加剧过拟合。**对策**：接受"长尾类预测不准"，把指标重心放到 Top-5 |
| 4 | **OTHER 是个垃圾桶** | 🟡 低 | 18.8% 的样本在 OTHER 里，模型学不到这个类的特征。**对策**：接受它是"无法归类"，不要指望分类器区分 OTHER 内部 |

## 九、复现命令

本文所有数字都来自以下命令（均在项目根目录执行）：

```bash
# 结构对比 + 三组 F1（第六节）
python scripts/spike_align.py
#   -> outputs/spike_align.json

#   -> outputs/scan_result.json

# 带推理的连接本仓库自身（第六节 6.5）
python scripts/scan_project.py src/ \
  --checkpoint <检测权重目录>/best \
  --output outputs/scan_src_inference.json --no-code
#   -> outputs/scan_src_inference.json

# 分类数据分布（第二节）
python -c "import json,collections; \
  c=collections.Counter(r['cwe'] for r in map(json.loads, \
  open('data/processed/cvefixes_classification_train.jsonl',encoding='utf-8'))); \
  print(len(c), c.most_common(5))"
```
